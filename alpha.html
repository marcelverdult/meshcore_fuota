Alpha-Test: Was du tun musst

Repeater holen sich neue Firmware per Funk, ohne dass jemand aufs Dach muss. Du hilfst beim Test: Du spielst eine Datei auf deinen Repeater, richtest ihn ein und wartest. Du brauchst nur die Abschnitte 1 bis 7 und die Paket-Tabelle weiter unten. Der Rest ist für Neugierige.

Es gibt genau 2 Downloads. Das Empfänger-Paket 1.17 bekommen alle Geräte außer einem. Das Seed-Paket 1.18 bekommt nur dieses eine Gerät je Region.

Alpha test: what you need to do

Repeaters fetch new firmware over the air, and nobody has to climb a roof. You help with the test: you put one file on your repeater, set it up and wait. You need only sections 1 to 7 and the package table further down. The rest is for the curious.

There are exactly 2 downloads. All devices except one get the receiver package 1.17. Only that one device per region gets the seed package 1.18.

1. Allein passiert nichts

1. Alone, nothing happens

Ein einzelner Repeater bekommt nie ein Update.

Ein Update wandert von Repeater zu Repeater. Steht dein Repeater allein, hört er niemanden, der es ihm anbietet. Dann wartet er ohne Ende.

In deiner Region laufen immer mindestens 2 Test-Repeater. Die Region heißt in MeshCore auch Flood-Scope. Alle Test-Repeater stellen dieselbe Region ein (Schritt 5) und stehen in Funkreichweite zueinander.

Genau einer davon ist der Seed. Der Seed hat das Update schon und bietet es den anderen an. Die anderen sind Empfänger: Sie holen sich das Update vom Seed.

Du hast mehrere Geräte? Auch mehrere Geräte von dir zählen. Ein Gerät wird Seed, die anderen werden Empfänger. Dann geht es allein.

Du hast nur ein Gerät? Such dir Mit-Tester aus deiner Region, am besten im Telegram-Thread (alternativ im Discord). Sprich mit ihnen ab, wer den Seed stellt. Eine Freigabe von uns brauchst du dafür nicht.

A single repeater never gets an update.

An update travels from repeater to repeater. If your repeater stands alone, it hears nobody who offers it. Then it waits forever.

At least 2 test repeaters always run in your region. A region is also called a flood scope in MeshCore. All test repeaters set the same region (step 5) and stand within radio range of each other.

Exactly one of them is the seed. The seed already has the update and offers it to the others. The others are receivers: they fetch the update from the seed.

Do you have several devices? Several devices of yours count too. One device becomes the seed, the others become receivers. Then you can do it alone.

Do you have only one device? Look for fellow testers in your region, best in the Telegram thread (or in Discord). Agree with them who provides the seed. You need no approval from us for that.

2. Welche Datei ist für dich?

2. Which file is yours?

Empfänger-Paket 1.17: für alle

Für alle Geräte außer dem Seed. Dein Repeater holt sich damit das Update. Das Paket heißt auch Basis-Paket.

Der Dateiname enthält -base-:
meshcore-fuota-1.17.1-fuota1-base-<Board>-<SoftDevice>.uf2

Du findest es im Release v1.17.1-fuota1.

Seed-Paket 1.18: nur für einen

Nur für das eine Gerät je Region, das ihr als Seed abgesprochen habt.

Der Dateiname enthält -seed-:
meshcore-fuota-1.18.0-b5-seed-<Board>-<SoftDevice>.uf2

Du findest es im Vorab-Release v1.18.0-fuota5.

Receiver package 1.17: for everyone

For all devices except the seed. Your repeater fetches the update with it. The package is also called the base package.

The file name contains -base-:
meshcore-fuota-1.17.1-fuota1-base-<board>-<SoftDevice>.uf2

You find it in the release v1.17.1-fuota1.

Seed package 1.18: for one only

Only for the one device per region that you agreed on as the seed.

The file name contains -seed-:
meshcore-fuota-1.18.0-b5-seed-<board>-<SoftDevice>.uf2

You find it in the pre-release v1.18.0-fuota5.

Das Seed-Paket trägt die Firmware 1.18.0 und das Update von 1.17.1 auf 1.18.0. Der Seed bietet es seinen Nachbarn an. Die Empfänger laufen mit 1.17.1-fuota1 und holen es von ihm.

Wähle bei beiden das Board und das SoftDevice deines Geräts. Das SoftDevice ist der Teil am Ende des Dateinamens, zum Beispiel s140-6.1.1. Die Namen aller Boards stehen in der Tabelle in den Details unten.

Spielen alle ihr eigenes Seed-Paket auf, weiß niemand mehr, woher das Update kommt. Dann können wir den Test nicht auswerten.

The seed package carries the firmware 1.18.0 and the update from 1.17.1 to 1.18.0. The seed offers it to its neighbours. The receivers run 1.17.1-fuota1 and fetch it from the seed.

For both, choose the board and the SoftDevice of your device. The SoftDevice is the part at the end of the file name, for example s140-6.1.1. The names of all boards are in the table in the details below.

If everyone installs their own seed package, nobody knows any more where the update came from. Then we cannot evaluate the test.

3. Die alte Version muss weg

3. The old version has to go

Warst du beim ersten Test dabei?

Dann läuft auf deinen Repeatern vielleicht noch die alte Test-Version (1.17.1-b2 oder 1.18.0-b3). Sie passt nicht mehr. Spiel auf jeden Repeater das neue Paket, auch auf den zweiten und dritten. Die alten Pakete sind zurückgezogen. Lösche sie aus deinem Download-Ordner, damit du sie nicht verwechselst.

So prüfst du es: Tippe in der USB-Konsole ver. Ein Empfänger antwortet v1.17.1-fuota1 (Build: 14 Aug 2026). Der Seed zeigt v1.18.0-fuota5. Steht da etwas anderes, spiel das Paket neu auf.

Diese Antworten stehen im Code im Code geprüft. Das Release lief noch auf keinem Gerät. Weicht deine Antwort ab, schreib es uns.

Did you take part in the first test?

Then your repeaters may still run the old test version (1.17.1-b2 or 1.18.0-b3). It no longer fits. Put the new package on every repeater, also the second and the third. The old packages are withdrawn. Delete them from your download folder so that you do not mix them up.

How to check: type ver in the USB console. A receiver answers v1.17.1-fuota1 (Build: 14 Aug 2026). The seed shows v1.18.0-fuota5. If it says anything else, install the package again.

These answers are in the code checked in the code. The release has not run on any device yet. If your answer differs, tell us.

4. Die Schritte

4. The steps

  1. Seed festlegen. Mindestens 2 Test-Repeater in deiner Region, genau einer davon Seed.
  2. Board finden. Such in der Tabelle weiter unten die Zeile mit deinem Gerät, zum Beispiel RAK4631.
  3. Datei laden. Empfänger nehmen die Datei mit -base- im Namen, der Seed die mit -seed-.
  4. Aufspielen. USB anstecken, 2-mal schnell Reset drücken und die Datei auf das neue Laufwerk ziehen. Tu das nur an Knoten, die du gut erreichst.
  5. Einrichten. Öffne die USB-Konsole, ein Terminal-Programm am USB-Anschluss deines Repeaters. Tippe diese Befehle und ersetze die Teile in spitzen Klammern:
    • password <dein Passwort> (höchstens 15 Zeichen, nicht password)
    • set name FUOTA <Spitzname> 1.17.1-fuota1 (beim Seed: 1.18.0-fuota5)
    • region default hansemesh (hansemesh ist ein Beispiel: Nimm den Namen der Region deines Netzes, auf allen Geräten gleich)
    • set lat <Breite> und set lon <Länge> (grob reicht)
    • set advert.interval 240
  6. Prüfen. ver zeigt die Version aus Abschnitt 3. Ein Empfänger, dem noch niemand ein Update angeboten hat, meldet mit fuota info den Satz no update. Beim Seed steht dort passing on update 950257b4.
  7. Warten. Tu nichts weiter. Das Holen dauert Stunden bis Tage (Abschnitt 5). Danach wartet der Repeater ab Werk noch 7 Tage, bevor er das Update anwendet.
  1. Pick the seed. At least 2 test repeaters in your region, exactly one of them the seed.
  2. Find your board. Look up the row with your device in the table further down, for example RAK4631.
  3. Download the file. Receivers take the file with -base- in its name, the seed the one with -seed-.
  4. Install it. Plug in USB, press Reset twice quickly and drag the file onto the new drive. Do this only on nodes that you can reach easily.
  5. Set up. Open the USB console, a terminal program on the USB port of your repeater. Type these commands and replace the parts in angle brackets:
    • password <your password> (15 characters at most, not password)
    • set name FUOTA <nickname> 1.17.1-fuota1 (on the seed: 1.18.0-fuota5)
    • region default hansemesh (hansemesh is an example: use the name of your network's region, the same on all devices)
    • set lat <latitude> and set lon <longitude> (rough is enough)
    • set advert.interval 240
  6. Check. ver shows the version from section 3. A receiver that nobody has offered an update yet answers fuota info with no update. On the seed you see passing on update 950257b4 there.
  7. Wait. Do nothing else. Fetching takes hours to days (section 5). After that the repeater waits 7 more days by default before it applies the update.

5. Warum es dauert, und warum manchmal gar nichts kommt

5. Why it takes long, and why sometimes nothing comes

Der Seed sagt seinen direkten Nachbarn: „Ich habe ein Update.“ Das heißt Angebot. Direkte Nachbarn sind Repeater in Funkreichweite. Der Seed beginnt mit Abständen von 10 Sekunden und verdoppelt sie, bis zu 2 Tagen.

Weiter entfernte Repeater erreicht er nur mit einer Flut. Das ist eine Nachricht an alle Repeater der Region. Der Seed schickt sie in der ersten Woche höchstens einmal am Tag, danach höchstens einmal je Woche im Code geprüft. Das ist Absicht: So bleibt das Mesh frei für normale Nachrichten.

Wer das Angebot nicht hört, fragt nicht. Dein Repeater meldet sich erst, wenn er ein Angebot gehört hat. Geht das Angebot verloren, wartet er auf das nächste.

The seed tells its direct neighbours: “I have an update.” That is called an offer. Direct neighbours are repeaters within radio range. The seed starts with gaps of 10 seconds and doubles them, up to 2 days.

It reaches repeaters farther away only with a flood. That is a message to all repeaters of the region. The seed sends it at most once a day in the first week, and at most once a week after that checked in the code. That is on purpose: it keeps the mesh free for normal messages.

Whoever does not hear the offer does not ask. Your repeater speaks up only after it has heard an offer. If the offer is lost, it waits for the next one.

Ein Angebot kann aus diesen Gründen verloren gehen:

  • Viel Verkehr im Mesh: Zwei Pakete gleichzeitig stören sich.
  • Falsche oder keine Region: Das Angebot kommt in deiner Region nie an.
  • Zu weit weg oder schlechter Empfang.

An offer can get lost for these reasons:

  • Much traffic in the mesh: two packets at the same time disturb each other.
  • Wrong or no region: the offer never arrives in your region.
  • Too far away or poor reception.

Hat dein Repeater das Angebot gehört, fragt er zurück. Die Frage geht auf dem Weg zurück, den das Angebot genommen hat. Bleibt sie 2-mal ohne Antwort, schickt er sie einmal als Flut, also an alle. Das klappt, dauert aber: Ein Repeater schickt höchstens eine solche Flut-Anfrage je Stunde im Code geprüft.

Es sind nur wenige Nachrichten. Geht eine davon verloren, verschiebt sich alles bis zum nächsten Versuch. Darum kann es Tage dauern. Das ist im Test normal.

Ein Hop ist ein Sprung von einem Repeater zum nächsten. Im Test gibt es nur wenige FUOTA-Repeater. Darum können zwischen Seed und dir mehrere normale Repeater liegen. Jeder Hop kann ein Paket verlieren. Je mehr Hops, desto größer das Risiko.

Später wird es schneller. Das Empfänger-Paket 1.17.1-fuota1 gibt selbst nichts weiter. Es holt das Update nur. Erst nach dem Update auf 1.18 bietet jeder Repeater es seinen Nachbarn an. Haben viele Repeater FUOTA, muss nicht mehr alles vom Seed kommen. Hört ein Repeater mehrere Anbieter, merkt er sich bis zu 4 und wechselt, wenn einer nicht antwortet.

If your repeater heard the offer, it asks back. The question goes back along the way the offer took. If it stays unanswered twice, the repeater sends the question once as a flood, so to everybody. That works, but it takes time: a repeater sends such a flood request at most once an hour checked in the code.

It is only a few messages. If one of them is lost, everything shifts to the next try. That is why it can take days. In the test that is normal.

A hop is a jump from one repeater to the next. In the test there are only a few FUOTA repeaters. So several normal repeaters can lie between the seed and you. Each hop can lose a packet. The more hops, the greater the risk.

Later it gets faster. The receiver package 1.17.1-fuota1 passes nothing on itself. It only fetches the update. Only after the update to 1.18 does every repeater offer it to its neighbours. If many repeaters run FUOTA, not everything has to come from the seed. If a repeater hears several providers, it remembers up to 4 and switches when one does not answer.

6. Der Analyzer hört nur zu

6. The analyzer only listens

Der Analyzer ist eine Webseite, die das Mesh zeigt. Stell dir vor, du stehst vor einem Haus und hörst durchs Fenster, wie drinnen jemand redet. Du verstehst nur Bruchstücke. So ähnlich arbeitet der Analyzer. Er fragt deinen Repeater nicht. Er kennt nur die Funkpakete, die ein Observer in der Nähe mitbekommt. Ein Observer ist ein Knoten, der gehörte Pakete ins Internet weiterreicht.

Im Tab Rollout stehen zwei Quellen nebeneinander im Code geprüft. Die eine sind Statusmeldungen, die ein Repeater selbst sendet. Das tut er nur mit Standard-Region (der Region, in der er flutet) und höchstens 8-mal in 24 Stunden. Die andere sind Angebote, die ein Observer gehört hat. Ein gehörtes Angebot nennt, wie viele Seiten (Teile des Updates) der Absender hat. Dieser Stand kann veraltet sein.

Fehlt ein Wert, zeigt der Analyzer einen Strich. Alle Zahlen sind Mindestwerte.

The analyzer is a web page that shows the mesh. Imagine you stand in front of a house and hear someone talk inside through the window. You catch only fragments. The analyzer works a bit like that. It does not ask your repeater. It knows only the radio packets that an observer nearby catches. An observer is a node that passes the packets it hears on to the internet.

The Rollout tab puts two sources side by side checked in the code. One is status messages that a repeater sends itself. It does so only with a default region (the region in which it floods) and at most 8 times in 24 hours. The other is offers that an observer has heard. A heard offer says how many pages (parts of the update) its sender holds. That state may already be out of date.

If a value is missing, the analyzer shows a dash. All numbers are lower bounds.

Region setzen

Setting the region

Eine Region heißt in MeshCore auch Flood-Scope. Ein Knoten flutet nur in seiner Region. Setze auf jedem Testrepeater die Region deines Mesh als Standard-Region. Gib in der USB-Konsole region default hansemesh ein. Der Knoten antwortet default scope is now hansemesh. Das Beispiel gilt für HanseMesh. Regionsnamen sind Freitext und je Netz verschieden. Nimm den Namen deines Netzes. Die Region bleibt gespeichert, auch über einen Neustart gemessen.

Ohne Standard-Region zeigt der Analyzer keinen Repeater mit Statusmeldung. Der Knoten verwirft seine Statusmeldungen (fuota: status E3 not sent, no default region). Seine Update-Angebote gehen nur an direkte Nachbarn (fuota info: no default region: not flooded) gemessen.

Mit Region sendet der Knoten die Statusmeldungen in die Region gemessen. Auch seine Update-Angebote flutet er dann dorthin im Code geprüft. Statusmeldungen sind gedrosselt, höchstens 8 in 24 Stunden.

A region is also called a flood scope in MeshCore. A node floods only in its region. On every test repeater, set the region of your mesh as the default region. In the USB console, enter region default hansemesh. The node answers default scope is now hansemesh. The example is for HanseMesh. Region names are free text and differ from network to network. Use the name of your network. The region stays stored, even across a restart measured.

Without a default region, the analyzer shows no repeater with a status message. The node discards its status messages (fuota: status E3 not sent, no default region). Its update offers only reach direct neighbours (fuota info: no default region: not flooded) measured.

With a region, the node sends its status messages into the region measured. It then floods its update offers there too checked in the code. Status messages are throttled, at most 8 in 24 hours.

Beobachten

Watching

fuota info zeigt am Gerät den Stand in der USB-Konsole. Als angemeldeter Admin fragst du ihn auch übers Mesh ab im Code geprüft. Dort geben fuota info und fuota status dieselbe Kurzantwort. Per USB gibt fuota status eine technische Zeile, fuota info die Kurzantwort im Code geprüft. Das ist am Gerät noch nicht gemessen offen.

Von außen siehst du die Kampagne im Analyzer (Abschnitt 6). Er zeigt die Kampagne erst, wenn ein Observer Angebote oder Daten hört. Der Stand 1.17.1-fuota1 bietet selbst keine Kampagne an. Steht dort keine Kampagne, gilt die Anzeige am Gerät.

Der Analyzer zeigt die Alpha-Kampagne im Feld beobachtet. Du findest sie auf der Seite FUOTA-Kampagnen im Tab Aktivität. Was der Tab Rollout zusammenführt, steht in Abschnitt 6.

Der Weg zwischen Anbieter und Empfänger darf über normale MeshCore-Repeater (Stock, also unverändert) führen. Die Angebote laufen als gewöhnliche Gruppen-Daten-Flut, die Stock-Repeater nach Region weiterleiten im Code geprüft. Am Testaufbau lief ein P1 mit unveränderter Stock-Firmware als Relais gemessen.

Im ersten Test kam das geflutete Angebot über das Mesh bis zu 6 Hops (Sprüngen von Repeater zu Repeater) weit im Feld beobachtet. Ein Empfänger bekam Datenpakete über 2 Repeater hintereinander, von denen der Analyzer nie FUOTA-Pakete gehört hat, bis zum 15.11. 48 von 174 im Feld beobachtet. Ein ganzes Update kam auf diesem Weg noch nicht an. Anfragen gingen auf dem Rückweg verloren. Von 73 gehörten Pfad-Anfragen kamen 35 beim letzten Repeater vor dem Anbieter an im Feld beobachtet.

Deshalb fragt der Empfänger zuerst auf dem Rückweg des Angebots. Bleibt die Anfrage 2-mal ohne Antwort, schickt er sie einmal als Flut (Abschnitt 5). Der Anbieter meldet ihm den Weg zurück, den die Flut genommen hat. Danach fragt der Empfänger auf diesem Weg. Das steht im Code der 1.17.1-Linie im Code geprüft. Das Release-Image enthält die Zähler dazu, geprüft an der UF2-Datei gemessen. Ob die Flut-Anfrage im Feld ankommt, ist offen. Melde weiter, ob Stock-Repeater dazwischen lagen.

Zum Probestart: Ein frisch aktualisierter Knoten bestätigt die neue Version erst, wenn er ein Funkpaket hört und selbst eins sendet. Dafür hat er je nach Knoten zwischen 15 Minuten und 6 Stunden Zeit. Hört er bis dahin nichts, startet er neu. Nach 3 Probestarts ohne Bestätigung läuft wieder die alte Firmware. Einen neuen Versuch gibt es frühestens nach einem Tag im Code geprüft. Teste deshalb dort, wo dein Knoten andere Knoten hört.

Zur Dauer: Der Release-Takt begrenzt die Sendezeit (Airtime) auf 0,3 %. Damit brauchte ein Knoten 12,6 h für 174 Datenpakete gemessen. Das war ein einzelner Lauf am Testaufbau.

fuota info shows the state in the USB console on the device. As a logged-in admin you can also query it over the mesh checked in the code. Over the mesh, fuota info and fuota status give the same short answer. Over USB, fuota status gives a technical line and fuota info the short answer checked in the code. This is not yet measured on a device open.

From outside you can see the campaign in the analyzer (section 6). It shows the campaign only once an observer hears offers or data. The build 1.17.1-fuota1 offers no campaign itself. If no campaign shows, trust the display on the device.

The analyzer shows the alpha campaign observed in the field. You find it on the FUOTA campaigns page, in the Activity tab. What the Rollout tab joins is explained in section 6.

The path between provider and receiver may run through normal MeshCore repeaters (stock, that is unchanged). The offers travel as ordinary group data floods, which stock repeaters forward by region checked in the code. On the bench a P1 with unchanged stock firmware ran as a relay measured.

In the first test the flooded offer travelled up to 6 hops (jumps from repeater to repeater) through the mesh observed in the field. One receiver got data packets over 2 repeaters in a row. The analyzer never heard FUOTA packets from them, 48 of 174 by 15 November observed in the field. No complete update has arrived this way yet. Requests were lost on the way back. Of 73 heard path requests, 35 reached the last repeater before the provider observed in the field.

So the receiver first asks along the way the offer took back. If the request stays unanswered twice, it sends it once as a flood (section 5). The provider reports back the path the flood took. After that the receiver asks along this path. This is in the code of the 1.17.1 line checked in the code. The release image holds the counters for it, checked on the UF2 file measured. Whether the flood request arrives in the field is open. Keep reporting whether stock repeaters lay in between.

On the test boot. A freshly updated node confirms the new version only after it hears a radio packet and sends one. Depending on the node, it has between 15 minutes and 6 hours for that. If it hears nothing by then, it restarts. After 3 test boots without confirmation the old firmware runs again. It tries again after one day at the earliest checked in the code. So test where your node hears other nodes.

On the duration: the release pace limits airtime to 0.3 %. At that pace a node needed 12.6 h for 174 data packets measured. That was a single run on the bench.

7 Tage Wartezeit und „sofort“

7 days of delay and “now”

Ein Release-Image installiert ein fertig geholtes Update nicht sofort. Ab Werk steht auto delay: Der Knoten wartet 7 Tage und installiert das Update danach. In dieser Woche lässt sich ein Update noch zurückziehen. Der Release-Build lässt sich nicht mit kürzerer Wartezeit bauen im Code geprüft.

Wer nicht warten will, gibt am Knoten in der USB-Konsole fuota auto now ein. Der Knoten installiert dann, sobald das Update vollständig da ist. Setze das am Anfang.

A release image does not install a fetched update at once. The factory setting is auto delay: the node waits 7 days and installs the update afterwards. During that week an update can still be withdrawn. The release build cannot be built with a shorter delay checked in the code.

If you do not want to wait, type fuota auto now in the USB console of the node. The node then installs as soon as the update is complete. Set this at the start.

Ohne USB: Update per Bluetooth

Without USB: update over Bluetooth

Kommst du an dein Gerät nicht per USB heran, nimm die OTA-ZIP-Datei. Sie bringt dieselbe Firmware wie die UF2 per Bluetooth auf das Gerät. Das Release führt 18 ZIP-Dateien.

Die ZIP-Dateien sind aus den UF2 abgeleitet und gegen sie geprüft. Per Bluetooth am Gerät sind sie nicht verifiziert offen. Wer USB hat, nimmt die UF2.

Mit den ZIP-Dateien des ersten Tests liefen 2 Boards am Gerät, je ein Lauf gemessen. Es sind der Seeed SenseCAP Solar P1 (S140 7.3.0) und ein FakeTec (S140 6.1.1, Bootloader 0.9.2-OTAFIX2.3-BP1.4 laut INFO_UF2.TXT).

Mit einem älteren Bootloader (OTAFIX 1.x, DFU-Name AdaDFU) ist der Weg nicht belegt offen. Ein FakeTec, das als AdaDFU warb, verlor bei schwachem Signal Pakete. Nach dem Aktivieren meldete es sich weder am USB noch per Bluetooth zurück. Die Ursache ist offen. Der Name passt zu OTAFIX 1.x, die Version selbst ist nicht gemessen. Mit dem Handy ist der Weg ungetestet offen. Die übrigen Boards liefen nie per Bluetooth.

Hast du USB, installiere lieber die UF2. Lies vor dem Update die Zeile in INFO_UF2.TXT, die mit UF2 Bootloader beginnt. Steht dort OTAFIX 1.x, nimm die UF2.

  1. Nimm den Namen der UF2 ohne .uf2, dazu -ota.zip. Die ZIP-Dateien liegen im Release v1.17.1-fuota1.
  2. Vergleiche die Prüfsumme mit SHA256SUMS-ota desselben Releases. SHA256SUMS gilt nur für die UF2.
  3. Lass Funkwerte und Region, wie sie sind. Im ersten Test blieben sie beim P1 und beim FakeTec gleich gemessen.
  4. Schick dem Repeater start ota. Er antwortet OK - BLE DFU of the bootloader in 5 s und meldet, dass er bis zu einem Update oder Stromwechsel offline bleibt gemessen.
  5. Nach 5 s wirbt er als DFU-Gerät, am P1 als SCAP_DFU, am FakeTec mit OTAFIX 2.3 als PROM_DFU. Bis das Update fertig ist, arbeitet er nicht als Repeater.
  6. Übertrage die ZIP per Bluetooth. Am Mac lief das mit einem Projektskript, das nicht zu den Releases gehört. Auf dem Handy wählst du in nRF Connect das DFU-Gerät und die ZIP offen.
  7. Danach startet der Knoten von selbst, am P1 nach etwa 15 s, am FakeTec nach höchstens 8 s gemessen. Prüfe ver, fuota status und fuota info.

Am P1 dauerte die Übertragung der Basis-ZIP des ersten Tests 134,6 s, am FakeTec 199,5 s gemessen.

Nur ein DFU-Gerät darf in der Nähe sein, sonst überschreibst du vielleicht ein fremdes. Bleib dicht am Gerät. Das FakeTec mit AdaDFU verlor Pakete. Ob Signal oder Bootloader der Grund war, ist nicht getrennt offen. Bleibt das Gerät hängen, trenne den Strom. Dem FakeTec mit AdaDFU half das nicht. Halte darum den USB-Zugang bereit.

If you cannot reach your device over USB, use the OTA ZIP file. It puts the same firmware as the UF2 on the device over Bluetooth. The release carries 18 ZIP files.

The ZIP files are derived from the UF2 files and checked against them. They are not verified on a device over Bluetooth open. If you have USB, use the UF2.

With the ZIP files of the first test, 2 boards have run on a device, one run each measured. They are the Seeed SenseCAP Solar P1 (S140 7.3.0) and a FakeTec (S140 6.1.1, bootloader 0.9.2-OTAFIX2.3-BP1.4 according to INFO_UF2.TXT).

With an older bootloader (OTAFIX 1.x, DFU name AdaDFU) the way is not proven open. A FakeTec that advertised as AdaDFU lost packets at a weak signal. After the activation it did not come back over USB or Bluetooth. The cause is open. The name fits OTAFIX 1.x, the version itself is not measured. From a phone the way is untested open. The remaining boards never ran over Bluetooth.

If you have USB, install the UF2 instead. Before the update, read the line in INFO_UF2.TXT that starts with UF2 Bootloader. If it shows OTAFIX 1.x, use the UF2.

  1. Take the name of the UF2 without .uf2, plus -ota.zip. The ZIP files are in the release v1.17.1-fuota1.
  2. Compare the checksum with SHA256SUMS-ota of the same release. SHA256SUMS applies to the UF2 only.
  3. Leave radio values and region as they are. In the first test they stayed the same on the P1 and the FakeTec measured.
  4. Send the repeater start ota. It replies OK - BLE DFU of the bootloader in 5 s and says it stays offline until an update or a power cycle measured.
  5. After 5 s it advertises as a DFU device, on the P1 as SCAP_DFU, on the FakeTec with OTAFIX 2.3 as PROM_DFU. Until the update is done, it does not work as a repeater.
  6. Transfer the ZIP over Bluetooth. On the Mac this ran with a project script that is not part of the releases. On a phone you pick the DFU device and the ZIP in nRF Connect open.
  7. Then the node starts by itself, on the P1 after about 15 s, on the FakeTec after 8 s at most measured. Check ver, fuota status and fuota info.

On the P1 the transfer of the base ZIP of the first test took 134.6 s, on the FakeTec 199.5 s measured.

Only one DFU device may be nearby, or you may overwrite someone else's. Stay close to the device. The FakeTec with AdaDFU lost packets. Whether the signal or the bootloader was the reason is not separated open. If the device gets stuck, cut the power. That did not help the FakeTec with AdaDFU. So keep USB access ready.
