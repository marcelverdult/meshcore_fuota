Alpha-Test: Repeater, die sich selbst updaten

Du flasht Testrepeater mit 1.17.1-fuota1. Dieser Stand holt Updates per Funk und wendet sie an. Er bietet selbst keine an und leitet keine weiter. Er ist die Ausgangsbasis, damit ein späteres 1.18 von Repeater zu Repeater laufen kann. Spiel ihn nur auf Knoten, die du gut erreichst.

Stand 18. November 2026: Der zweite Alpha-Test nutzt das Release v1.17.1-fuota1. Wer beim ersten Test dabei war, flasht neu: Die Pakete 1.17.1-b2 und 1.18.0-b3 sind zurückgezogen und passen nicht zur neuen Kampagne. Alpha test: repeaters that update themselves

You flash test repeaters with 1.17.1-fuota1. This build fetches updates over the air and applies them. It offers none itself and passes none on. It is the starting point so that a later 1.18 can run from repeater to repeater. Use it only on nodes that you can reach easily.

Status as of 18 November 2026: The second alpha test uses the release v1.17.1-fuota1. If you took part in the first test, flash again. The packages 1.17.1-b2 and 1.18.0-b3 have been withdrawn and do not fit the new campaign. These exact signed release files have not yet run on any device. The bench runs used the test image. This release is itself the first test open.

So läuft der Test

How the test runs

  1. Such dir ein paar andere Tester und bildet eine Gruppe. Ihr teilt mehrere Testrepeater unter euch auf. Alle Geräte der Gruppe liegen in Funkreichweite zueinander.
  2. Alle flashen das Basispaket 1.17.1-fuota1 per USB (Tabelle unten) und setzen die Region ihres Netzes (Abschnitt Region setzen).
  3. Der Knoten holt Updates per Funk, prüft die Signatur, startet zur Probe und bestätigt. Du tust nichts. Er bietet selbst keine Updates an und leitet keine weiter. Einen Termin für ein späteres 1.18 nennen wir hier nicht.
  4. Du beobachtest den Stand und meldest, was passiert ist.

Richte jeden Testrepeater ein wie jeden anderen Repeater. Tippe die Befehle in der USB-Konsole.

  • Admin-Passwort: password <Passwort>, höchstens 15 Zeichen. Die Pakete sind Release-Images und haben ab Werk keines. Für die USB-Befehle brauchst du es nicht, es gilt für den Admin-Zugang aus der Ferne. Der Knoten antwortet mit password now: und dem Passwort im Code geprüft. Mit einem Release-Image am Gerät ist das noch nicht gemessen offen.
  • Das Passwort password geht nicht, ein leeres auch nicht. Ein Release-Image lehnt beide beim Admin-Login ab, auch wenn alte gespeicherte Einstellungen sie enthalten im Code geprüft. Wer password password tippt, bekommt die Zeile Err - no admin login with an empty password (in a release: nor with the stock default) im Code geprüft. Wähle ein anderes Passwort. Mit einem Release-Image am Gerät ist das noch nicht gemessen offen.
  • GPS-Position: set lat <Breite> und set lon <Länge>. Die Antwort ist jeweils OK im Code geprüft.
  • Name mit der Version: set name FUOTA-Test 1.17. Die Antwort ist OK. So siehst du im Analyzer, welcher Repeater welcher ist. Der Name geht mit dem nächsten Advert raus, advert sendet ihn sofort im Code geprüft. Er bleibt nach einem Update stehen, auch wenn der Repeater dann 1.18 trägt im Code geprüft. Für ein Update per Funk ist das am Gerät noch nicht gemessen offen.
  • LoRa-Parameter: set radio <MHz>,<Bandbreite>,<SF>,<CR> mit den Werten deines Netzes. Die Antwort ist OK - reboot to apply, danach startest du den Knoten neu im Code geprüft.
  • Region: siehe Abschnitt Region setzen.
  • Advert-Intervall: set advert.interval 240. 1.17.1-b2 erlaubte 0 (aus) und 60 bis 240 Minuten im Code geprüft. Es startete mit einem Intervall unter 60 Minuten und setzte es beim ersten Speichern einer Einstellung auf 0 im Code geprüft. Dann sendet der Knoten keine Adverts mehr und erscheint nicht im Analyzer. Ob 1.17.1-fuota1 sich genauso verhält, ist nicht neu geprüft offen.
  • Repeat an lassen: get repeat zeigt > on, ab Werk ist es an. Mit set repeat on schaltest du es wieder ein, die Antwort ist OK - repeat is now ON.

Mehrere Gruppen können unabhängig voneinander testen, je mehr, desto besser.

  1. Find a few other testers and form a group. You split several test repeaters among yourselves. All devices of the group are within radio range of each other.
  2. Everyone flashes the base package 1.17.1-fuota1 over USB (table below) and sets the region of their network (section Setting the region).
  3. The node fetches updates over the air, checks the signature, starts them on trial and confirms. You do nothing. It offers no updates itself and passes none on. We name no date for a later 1.18 here.
  4. You watch the state and report what happened.

Set up every test repeater like any other repeater. Type the commands in the USB console.

  • Admin password: password <password>, 15 characters at most. The packages are release images and have none from the factory. You do not need it for the USB commands, it is for admin access from afar. The node answers with password now: and the password checked in the code. With a release image on a device this is not yet measured open.
  • The password password does not work, and neither does an empty one. A release image refuses both at the admin login, even when old saved settings hold them checked in the code. If you type password password, you get the line Err - no admin login with an empty password (in a release: nor with the stock default) checked in the code. Choose another password. With a release image on a device this is not yet measured open.
  • GPS position: set lat <latitude> and set lon <longitude>. Each answer is OK checked in the code.
  • Name with the version: set name FUOTA-Test 1.17. The answer is OK. That way you can tell in the analyzer which repeater is which. The name goes out with the next advert, and advert sends it at once checked in the code. It stays after an update, even when the repeater then runs 1.18 checked in the code. For an update over the air, this is not yet measured on a device open.
  • LoRa parameters: set radio <MHz>,<bandwidth>,<SF>,<CR> with the values of your network. The answer is OK - reboot to apply, then you restart the node checked in the code.
  • Region: see the section Setting the region.
  • Advert interval: set advert.interval 240. 1.17.1-b2 allowed 0 (off) and 60 to 240 minutes checked in the code. It started with an interval under 60 minutes and set it to 0 when you first saved a setting checked in the code. Then the node sends no adverts and does not show up in the analyzer. Whether 1.17.1-fuota1 behaves the same is not newly checked open.
  • Keep repeat on: get repeat shows > on, it is on from the factory. With set repeat on you switch it back on, the answer is OK - repeat is now ON.

Several groups can test independently of each other, the more the better.

Region setzen

Setting the region

Setze auf jedem Testrepeater die Region deines Netzes als Default. Gib in der USB-Konsole region default hansemesh ein. Der Knoten antwortet default scope is now hansemesh. Das Beispiel gilt für HanseMesh. Regionsnamen sind Freitext und je Netz verschieden. Nimm den Namen deines Netzes. Die Region bleibt gespeichert, auch über einen Neustart gemessen.

Ohne Standard-Region zeigt der Analyzer keinen Repeater mit Statusmeldung. Der Knoten verwirft seine Statusmeldungen (fuota: status E3 not sent, no default region). Seine Update-Angebote gehen nur an direkte Nachbarn (fuota info: no default region: not flooded) gemessen.

Mit Region sendet der Knoten die Statusmeldungen in die Region gemessen. Auch seine Update-Angebote flutet er dann dorthin im Code geprüft. Statusmeldungen sind gedrosselt, höchstens 8 in 24 Stunden.

On every test repeater, set the region of your network as the default. In the USB console, enter region default hansemesh. The node answers default scope is now hansemesh. The example is for HanseMesh. Region names are free text and differ from network to network. Use the name of your network. The region stays stored, even across a restart measured.

Without a default region, the analyzer shows no repeater with a status message. The node discards its status messages (fuota: status E3 not sent, no default region). Its update offers only reach direct neighbours (fuota info: no default region: not flooded) measured.

With a region, the node sends its status messages into the region measured. It then floods its update offers there too checked in the code. Status messages are throttled, at most 8 in 24 hours.

Beobachten

Watching

fuota info zeigt am Gerät den Stand in der USB-Konsole. Als angemeldeter Admin fragst du ihn auch übers Mesh ab im Code geprüft. Dort gibt fuota status nur die Kurzantwort von fuota info, die ausführliche Anzeige gibt es nur per USB im Code geprüft. Das ist am Gerät noch nicht gemessen offen.

Von außen siehst du die Kampagne im Analyzer. Sie erscheint dort erst, wenn ein Observer (ein Knoten, der mithört und meldet) Angebote oder Daten hört. Der Stand 1.17.1-fuota1 bietet selbst keine Kampagne an. Steht dort keine Kampagne, gilt die Anzeige am Gerät.

Der Analyzer zeigt die Alpha-Kampagne im Feld beobachtet. Du findest sie auf der Seite FUOTA-Kampagnen im Tab Aktivität. Der Tab Rollout zeigt nur Repeater, die Statusmeldungen senden im Feld beobachtet. Das sind nur Knoten mit Standard-Region (Abschnitt Region setzen).

Der Weg zwischen Seed und Empfänger darf über normale MeshCore-Repeater (Stock) führen. Die Angebote laufen als gewöhnliche Gruppen-Daten-Flut, die Stock-Repeater nach Region weiterleiten im Code geprüft. Am Brett lief ein P1 mit unveränderter Stock-Firmware als Relais gemessen.

Im ersten Test kam das geflutete Angebot über das Mesh bis zu 6 Hops weit im Feld beobachtet. Ein Empfänger bekam Datenpakete über 2 Repeater hintereinander, von denen der Analyzer nie FUOTA-Pakete gehört hat, bis zum 15.11. 48 von 174 im Feld beobachtet. Ein ganzes Update kam auf diesem Weg noch nicht an. Viele Anfragen gingen auf dem Rückweg verloren. Von 73 gehörten Pfad-Anfragen kamen 35 beim letzten Repeater vor dem Anbieter an im Feld beobachtet.

Deshalb geht die Anfrage zuerst auf dem Rückweg des Angebots zum Anbieter. Bleibt sie zweimal ohne Antwort, schickt der Empfänger sie einmal als Flut. Der Anbieter meldet ihm den Weg zurück, den die Flut genommen hat. Danach fragt der Empfänger auf diesem Weg. Das steht im Entwicklungszweig im Code geprüft. Ob 1.17.1-fuota1 es schon enthält, ist offen. Melde weiter, ob Stock-Repeater dazwischen lagen.

Zum Probestart: Ein frisch aktualisierter Knoten bestätigt die neue Version erst, wenn er ein Funkpaket hört und selbst eins sendet. Dafür hat er je nach Knoten zwischen 15 Minuten und 6 Stunden Zeit. Hört er bis dahin nichts, startet er neu. Nach drei solchen Starts kehrt er zur alten Version zurück. Einen neuen Versuch gibt es frühestens nach einem Tag im Code geprüft. Teste deshalb dort, wo dein Knoten andere Knoten hört.

Zur Dauer: Der Release-Takt hat 0,3 % Sendeanteil. Mit ihm brauchte ein Knoten 12,6 h für 174 Fragmente gemessen. Das war ein einzelner Lauf am Testaufbau.

fuota info shows the state in the USB console on the device. As a logged-in admin you can also query it over the mesh checked in the code. Over the mesh, fuota status gives only the short answer of fuota info, and the detailed display exists only over USB checked in the code. This is not yet measured on a device open.

From outside you can see the campaign in the analyzer. It appears there only once an observer (a node that listens and reports) hears offers or data. The build 1.17.1-fuota1 offers no campaign itself. If no campaign shows, trust the display on the device.

The analyzer shows the alpha campaign observed in the field. You find it on the FUOTA campaigns page, in the Activity tab. The Rollout tab shows only repeaters that send status messages observed in the field. Those are only nodes with a default region (section Setting the region).

The path between seed and receiver may run through normal MeshCore repeaters (stock). The offers travel as ordinary group data floods, which stock repeaters forward by region checked in the code. On the bench a P1 with unchanged stock firmware ran as a relay measured.

In the first test the flooded offer travelled up to 6 hops through the mesh observed in the field. One receiver got data packets over 2 repeaters in a row from which the analyzer never heard FUOTA packets, 48 of 174 by 15 November observed in the field. No complete update has arrived this way yet. Many requests were lost on the way back. Of 73 heard path requests, 35 reached the last repeater before the provider observed in the field.

So the request first goes back to the provider along the path the offer took. If it stays unanswered twice, the receiver sends it once as a flood. The provider reports back the path the flood took. After that the receiver asks along this path. This is in the development branch checked in the code. Whether 1.17.1-fuota1 already contains it is open. Keep reporting whether stock repeaters lay in between.

On the test boot. A freshly updated node confirms the new version only after it hears a radio packet and sends one. Depending on the node, it has between 15 minutes and 6 hours for that. If it hears nothing by then, it restarts. After three such starts it returns to the old version. It tries again after one day at the earliest checked in the code. So test where your node hears other nodes.

On the duration: the release pace has a 0.3 % send share. At that pace a node needed 12.6 h for 174 fragments measured. That was a single run on the bench.

Sieben Tage Wartezeit und „sofort“

Seven days of delay and “now”

Ein Release-Image installiert ein fertig geholtes Update nicht sofort. Ab Werk steht auto delay: Der Knoten wartet 7 Tage und installiert das Update danach. In dieser Woche lässt sich ein Update noch zurückziehen. Der Release-Build lässt sich nicht mit kürzerer Wartezeit bauen im Code geprüft.

Wer nicht warten will, gibt am Knoten in der USB-Konsole fuota auto now ein. Der Knoten installiert dann, sobald das Update vollständig da ist. Wir bitten dich, das am Anfang zu setzen.

A release image does not install a fetched update at once. The factory setting is auto delay: the node waits 7 days and installs the update afterwards. During that week an update can still be withdrawn. The release build cannot be built with a shorter delay checked in the code.

If you do not want to wait, type fuota auto now in the USB console of the node. The node then installs as soon as the update is complete. We ask you to set this at the start.

  • board, file name and whether the checksum matched

Ohne USB: Update per Bluetooth

Without USB: update over Bluetooth

Kommst du an dein Gerät nicht per USB heran, nimm die OTA-ZIP-Datei. Sie bringt dieselbe Firmware wie die UF2 per Bluetooth auf das Gerät. Das Release führt 18 ZIP-Dateien.

Die ZIP-Dateien sind aus den UF2 abgeleitet und gegen sie geprüft. Per Bluetooth am Gerät sind sie nicht verifiziert offen. Wer USB hat, nimmt die UF2.

Mit den ZIP-Dateien des ersten Tests liefen zwei Boards am Gerät, je ein Lauf gemessen. Es sind der Seeed SenseCAP Solar P1 (S140 7.3.0) und ein FakeTec (S140 6.1.1, Bootloader 0.9.2-OTAFIX2.3-BP1.4 laut INFO_UF2.TXT).

Mit einem älteren Bootloader (OTAFIX 1.x, DFU-Name AdaDFU) ist der Weg nicht belegt offen. Ein FakeTec, das als AdaDFU warb, verlor bei schwachem Signal Pakete. Nach dem Aktivieren meldete es sich weder am USB noch per Bluetooth zurück. Die Ursache ist offen. Der Name passt zu OTAFIX 1.x, die Version selbst ist nicht gemessen. Mit dem Handy ist der Weg ungetestet offen. Die übrigen Boards liefen nie per Bluetooth.

Hast du USB, flashe lieber die UF2. Lies vor dem Update die Zeile in INFO_UF2.TXT, die mit UF2 Bootloader beginnt. Steht dort OTAFIX 1.x, nimm die UF2.

  1. Nimm den Namen der UF2 ohne .uf2, dazu -ota.zip. Die ZIP-Dateien liegen im Release v1.17.1-fuota1.
  2. Vergleiche die Prüfsumme mit SHA256SUMS-ota desselben Releases. SHA256SUMS gilt nur für die UF2.
  3. Lass Funkwerte und Region, wie sie sind. Im ersten Test blieben sie beim P1 und beim FakeTec gleich gemessen.
  4. Schick dem Repeater start ota. Er antwortet OK - BLE DFU of the bootloader in 5 s und meldet, dass er bis zu einem Update oder Stromwechsel offline bleibt gemessen.
  5. Nach 5 s wirbt er als DFU-Gerät, am P1 als SCAP_DFU, am FakeTec mit OTAFIX 2.3 als PROM_DFU. Bis das Update fertig ist, arbeitet er nicht als Repeater.
  6. Übertrage die ZIP per Bluetooth. Am Mac lief das mit einem Projektskript, das nicht zu den Releases gehört. Auf dem Handy wählst du in nRF Connect das DFU-Gerät und die ZIP offen.
  7. Danach startet der Knoten von selbst, am P1 nach etwa 15 s, am FakeTec nach höchstens 8 s gemessen. Prüfe ver, fuota status und fuota info.

Am P1 dauerte die Übertragung der Basis-ZIP des ersten Tests 134,6 s, am FakeTec 199,5 s gemessen.

Nur ein DFU-Gerät darf in der Nähe sein, sonst überschreibst du vielleicht ein fremdes. Bleib dicht am Gerät. Das FakeTec mit AdaDFU verlor Pakete. Ob Signal oder Bootloader der Grund war, ist nicht getrennt offen. Bleibt das Gerät hängen, trenne den Strom. Dem FakeTec mit AdaDFU half das nicht. Halte darum den USB-Zugang bereit.

If you cannot reach your device over USB, use the OTA ZIP file. It puts the same firmware as the UF2 on the device over Bluetooth. The release carries 18 ZIP files.

The ZIP files are derived from the UF2 files and checked against them. They are not verified on a device over Bluetooth open. If you have USB, use the UF2.

With the ZIP files of the first test, two boards have run on a device, one run each measured. They are the Seeed SenseCAP Solar P1 (S140 7.3.0) and a FakeTec (S140 6.1.1, bootloader 0.9.2-OTAFIX2.3-BP1.4 according to INFO_UF2.TXT).

With an older bootloader (OTAFIX 1.x, DFU name AdaDFU) the way is not proven open. A FakeTec that advertised as AdaDFU lost packets at a weak signal. After the activation it did not come back over USB or Bluetooth. The cause is open. The name fits OTAFIX 1.x, the version itself is not measured. From a phone the way is untested open. The remaining boards never ran over Bluetooth.

If you have USB, flash the UF2 instead. Before the update, read the line in INFO_UF2.TXT that starts with UF2 Bootloader. If it shows OTAFIX 1.x, use the UF2.

  1. Take the name of the UF2 without .uf2, plus -ota.zip. The ZIP files are in the release v1.17.1-fuota1.
  2. Compare the checksum with SHA256SUMS-ota of the same release. SHA256SUMS applies to the UF2 only.
  3. Leave radio values and region as they are. In the first test they stayed the same on the P1 and the FakeTec measured.
  4. Send the repeater start ota. It replies OK - BLE DFU of the bootloader in 5 s and says it stays offline until an update or a power cycle measured.
  5. After 5 s it advertises as a DFU device, on the P1 as SCAP_DFU, on the FakeTec with OTAFIX 2.3 as PROM_DFU. Until the update is done, it does not work as a repeater.
  6. Transfer the ZIP over Bluetooth. On the Mac this ran with a project script that is not part of the releases. On a phone you pick the DFU device and the ZIP in nRF Connect open.
  7. Then the node starts by itself, on the P1 after about 15 s, on the FakeTec after 8 s at most measured. Check ver, fuota status and fuota info.

On the P1 the transfer of the base ZIP of the first test took 134.6 s, on the FakeTec 199.5 s measured.

Only one DFU device may be nearby, or you may overwrite someone else's. Stay close to the device. The FakeTec with AdaDFU lost packets. Whether the signal or the bootloader was the reason is not separated open. If the device gets stuck, cut the power. That did not help the FakeTec with AdaDFU. So keep USB access ready.
