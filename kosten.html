Was ein Update das Mesh kostet

Über Funk geht nur der Patch, beim kleinen Release 10.076 B gemessen. Das sind 60 Datenpakete an einen Nachbarn berechnet, und jeder Knoten sendet höchstens 0,3 % Airtime im Code geprüft. Für 152 verbundene Repeater um Hamburg sind es 1.300 bis 1.700 Datenpakete berechnet.

What an update costs the mesh

Only the patch travels over the air, 10,076 B for the small release measured. That is 60 data packets to one neighbour calculated, and every node sends at most 0.3 % airtime checked in the code. For 152 connected repeaters around Hamburg it takes 1,300 to 1,700 data packets calculated.

Airtime-Budget

Jeder Knoten sendet höchstens 0,3 % Airtime im Code geprüft. Das Budget ist eine harte Grenze für alle FUOTA-Pakete zusammen. Nur Knoten, die Nachbarn versorgen, senden Daten. Im Testaufbau galt ein Budget von 10 %. In FUOTAs eigener Rechnung war der höchste Anteil je 120 s 10,1 % berechnet. Das Funkmodul meldete 10,8 % gemessen. Der Unterschied sind die normalen lokalen Adverts (Selbstmeldungen) des Repeaters, alle 2 min, 449 ms. Ohne sie stimmt die Rechnung mit der gemessenen Sendezeit überein.

Kanallast

Jeder Sender nutzt höchstens sein Budget. In Hamburg hört ein Knoten im Median 2 Sender in Reichweite, im 90. Perzentil (p90) 6. Bei 0,3 % Budget sind es im dichtesten Zehntel bis rund 1,8 % Update-Verkehr berechnet. Bei 1 % sind es rund 6 % berechnet. Eine Anfrage nennt genau einen Anbieter. Auch wenn mehrere das Update haben, sendet für einen Fragenden immer nur einer. Die Zahlen für ganz Hamburg stehen unter Verteilung in Hamburg.

Airtime budget

Every node sends at most 0.3 % airtime checked in the code. The budget is a hard limit for all FUOTA packets together. Only nodes that supply neighbours send data. On the bench the budget was 10 %. By FUOTA's own count the highest share per 120 s was 10.1 % calculated. The radio module reported 10.8 % measured. The difference is the repeater's normal local adverts (self-announcements), every 2 min, 449 ms. Without them the calculation matches the measured transmit time.

Channel load

Each sender uses at most its budget. In Hamburg a node hears 2 senders in range (median). At the 90th percentile (p90) it hears 6. At 0.3 % the densest tenth sees up to about 1.8 % update traffic calculated. At 1 % it is about 6 % calculated. A request names exactly one provider. Even when several have the update, only one sends for a given puller. The figures for all of Hamburg are under Distribution in Hamburg.

Dauer je Hop

Ein Hop ist der Weg eines Updates von einem Knoten zu seinem direkten Nachbarn. Die Rechnung nimmt SF8, 1.721 ms je Datenpaket und 4-KB-Seiten berechnet.

  • Hop 1 braucht alle Datenpakete des Patches.
  • Jeder weitere Hop braucht nur eine Seite mehr, weil geprüfte Seiten sofort weitergehen.
  • Eine Seite sind 23,3 Datenpakete. Bei 0,3 % dauert jeder weitere Hop rund 3,7 h berechnet.
  • Bei 1 % sind es rund 1,1 h berechnet.
  • Im Testaufbau trifft die Rechnung. Hop 1 dauerte bei 10 % 464 s gemessen, gerechnet waren es 469 s. Hop 2 lag eine Seite dahinter gemessen.

Duration per hop

A hop is an update's way from one node to its direct neighbour. The calculation uses SF8, 1,721 ms per data packet and 4 KB pages calculated.

  • Hop 1 needs all data packets of the patch.
  • Each further hop needs only one page more, because checked pages move on at once.
  • A page is 23.3 data packets. At 0.3 % each further hop takes about 3.7 h calculated.
  • At 1 % it is about 1.1 h calculated.
  • On the bench the calculation holds. Hop 1 took 464 s at 10 % measured. The calculation gave 469 s. Hop 2 was one page behind measured.

Was das Modell nicht kann
  • Es rechnet keine Kollisionen ein, auch keine durch versteckte Knoten (die einander nicht hören).
  • Es rechnet keinen normalen Verkehr und keine Paketverluste ein.
  • Es nimmt einen Anbieter je Seite. Mehrere würden schneller liefern: im Testaufbau doppelt so schnell gemessen.
  • Ein Anbieter, der mehrere Nachbarn mit verschiedenem Stand versorgt, teilt sein Budget. Das rechnet das Modell nicht ein.
  • Nachbardaten gibt es nur von Repeatern, deren Nachbarn jemand abgerufen hat.
  • Die Patch-Größen stammen vom Stock-FakeTec mit -Os aus den Release-Tags.
  • Mit 33 Seiten passt der Compilerwechsel nicht hinter das Image (66 Seiten, 31 frei). Ein Knoten wendet ihn überlappend an, erst nach dem Fenster, in dem er weitergibt. Diese Wartezeit rechnet das Modell nicht ein.
  • Real dauert es eher länger: Kollisionen, Paketverluste und normaler Verkehr kommen dazu.
What the model cannot do
  • It does not model collisions, also none from hidden nodes (that cannot hear each other).
  • It does not model normal traffic or packet loss.
  • It assumes one provider per page. Several would deliver faster: on the bench twice as fast measured.
  • A provider that serves several neighbours with different states shares its budget. The model does not account for that.
  • Neighbour data exists only for repeaters whose neighbours somebody has fetched.
  • The patch sizes come from the stock FakeTec with -Os from the release tags.
  • At 33 pages the compiler change does not fit behind the 66-page image (31 free). A node applies it overlapping, only after the window in which it passes it on. The model does not include that wait.
  • Real runs tend to take longer: collisions, packet loss and normal traffic add to it.

Warum Patches klein bleiben

Das Ziel ist, dass alle dieselben signierten Images aus den Releases auf GitHub installieren. Dann erreicht ein Patch, eine Kampagne jeden Repeater mit FUOTA. Ein Knoten mit selbst gebautem Image bekommt keinen Patch von seinen Nachbarn. Signierte Releases gibt es noch nicht offen.

Einen Compilerwechsel wie von 1.17.1 nach 1.18.0 gibt es mit FUOTA nur mit Absicht. Die FUOTA-Builds frieren Compiler und Bibliotheken ein.

Eingefrorene Toolchain, reproduzierbarer Build

Ein Patch bleibt nur klein, wenn beide Images dieselbe Toolchain nutzen. Die Toolchain sind Compiler und Bibliotheken. Der Wechsel von GCC 7 auf GCC 14 machte aus 32,6 KB 219 KB gemessen. Beide Patches sind mit bsdiff und -Ofast gebaut.

Die Stock-Konfiguration von MeshCore erlaubt neuere Versionen:

  • die Platform ohne Version
  • die Toolchain und 14 Bibliotheken mit ^
  • transitive Bibliotheken (die Bibliotheken der Bibliotheken) ohne Version

Eine neue Bibliotheksversion ändert dort das Image, ohne dass sich der Quelltext ändert. Die FUOTA-Builds legen darum alles exakt fest:

  • Platform nordicnrf52 11.0.0
  • GCC 14.2.1 (toolchain-gccarmnoneeabi 1.140201.0)
  • Framework und Git-Bibliotheken per Commit
  • alle Bibliotheken, auch die transitiven, die ins Image gehen

Zwei Builds desselben Commits wichen nur an einer Stelle ab. Das ist der Build-Stempel der Funkbibliothek (__DATE__, __TIME__). Der Release-Build setzt SOURCE_DATE_EPOCH auf die Commit-Zeit.

  • Zwei Builds desselben Commits in verschiedenen Verzeichnissen sind byte-gleich gemessen.
  • Ein Linux-Build ist nicht byte-gleich zu einem macOS-Build. Das Toolchain-Paket einer Version enthält für beide Systeme dieselben 376 Objektdateien der C-Mathebibliothek. Im Archiv liegen sie in anderer Reihenfolge. Der Linker ordnet die Funktionen entsprechend anders: gleicher Code, Patch zwischen beiden 8.259 B gemessen.

Release-Images entstehen darum immer im selben Linux-Container:

  • Basis-Image per Digest und auf linux/arm64 festgelegt
  • PlatformIO 6.2.0 und seine Python-Pakete mit Version und Hash
  • dazu die festgelegten Versionen von oben
  • gebaut wird genau ein Commit

Zwei Läufe und ein unabhängiger Linux-Build ohne dieses Container-Image ergaben alle Images byte-gleich gemessen. Der unabhängige Build nutzte Python-Pakete ohne Hashes und einen anderen Pfad. Ob ein x86_64-Rechner dasselbe Image baut, ist nicht geprüft offen.

Patches entstehen immer gegen das archivierte Release-Image, das auf den Geräten läuft. Nie gegen einen Neubau. Ein Patch für das falsche Image zerstört nichts. Der Knoten zieht nur, wenn der Quell-Hash im Angebot zu seinem Image passt.

Kleineres Image, kleinere Patches

Der Adafruit-Core übersetzt nRF52-Firmware mit -Ofast, also auf Tempo. FUOTA-Builds übersetzen mit -Os, also auf Größe, und ändern außerdem:

  • USB: Die ungenutzten Klassen sind aus (Massenspeicher, HID, MIDI, Vendor, Video). Die serielle Schnittstelle bleibt, das UF2-Laufwerk gehört dem Bootloader.
  • Sensoren: Es fehlen die Treiber für
    • den Laser-Abstandssensor VL53L0X
    • das Infrarot-Thermometer MLX90614
    • den alten Drucksensor BMP085
    • den Bodenfeuchtesensor RAK12035
  • Funkbibliothek: Es fehlt die Tonausgabe.
  • Uhrenchip RX8130CE: Die Zeit wird ohne die Zeitzonen-Funktionen der C-Bibliothek gerechnet.
  • Einheits-Image (ein Image für alle Boards): kein Display-Treiber mehr, die Taste bleibt.

  • die Betreiber-Befehle über LoRa
  • das Release-Paket
  • die Härtung nach dem externen Review

Ein Image für alle Boards

Ein Image für alle unterstützten Boards heißt eine Kampagne für das ganze Gebiet. Bei einem Image je Modell:

  • Jedes Modell bräuchte eine eigene Kampagne mit eigenem Patch.
  • Ein Knoten könnte nur von Knoten desselben Modells holen.
  • Die Datenpakete vervielfachten sich mit der Zahl der Modelle.

Why patches stay small

The goal is that everyone installs the same signed images from the releases on GitHub. Then one patch, one campaign reaches every repeater with FUOTA. A node with a self-built image gets no patch from its neighbours. There are no signed releases yet open.

A compiler change like 1.17.1 to 1.18.0 happens with FUOTA only on purpose. The FUOTA builds freeze compiler and libraries.

Frozen toolchain, reproducible build

A patch stays small only when both images use the same toolchain. A toolchain is the compiler plus the libraries. The change from GCC 7 to GCC 14 turned 32.6 KB into 219 KB measured. Both patches use bsdiff and -Ofast.

The stock configuration of MeshCore allows newer versions:

  • the platform without a version
  • the toolchain and 14 libraries with ^
  • transitive libraries (the libraries of the libraries) without a version

A new library release changes the image there without any change in the source. The FUOTA builds therefore pin everything exactly:

  • platform nordicnrf52 11.0.0
  • GCC 14.2.1 (toolchain-gccarmnoneeabi 1.140201.0)
  • framework and git libraries by commit
  • all libraries, including the transitive ones that end up in the image

Two builds of one commit differed only in one place. That is the build stamp of the radio library (__DATE__, __TIME__). The release build sets SOURCE_DATE_EPOCH to the commit time.

  • Two builds of the same commit in different directories are byte-identical measured.
  • A Linux build is not byte-identical to a macOS build. The toolchain package of one version holds the same 376 object files for both systems. They belong to the C math library and sit in another order in the archive. The linker orders the functions accordingly: same code, patch between the two 8,259 B measured.

Release images therefore always come from the same Linux container:

  • base image pinned by digest and to linux/arm64
  • PlatformIO 6.2.0 and its Python packages pinned by version and hash
  • plus the pinned versions above
  • exactly one commit is built

Two runs and an independent Linux build without this container image gave byte-identical images measured. The independent build used Python packages without hashes and another path. Whether an x86_64 machine builds the same image is not checked open.

Patches are always built against the archived release image on the devices. Never against a rebuild. A patch for the wrong image breaks nothing. The node only pulls when the source hash in the offer matches its image.

Smaller image, smaller patches

The Adafruit core compiles nRF52 firmware with -Ofast, that is for speed. FUOTA builds compile with -Os, that is for size, and also change:

  • USB: the unused classes are off (mass storage, HID, MIDI, vendor, video). The serial port stays, the UF2 drive belongs to the bootloader.
  • Sensors: the drivers are missing for
    • the VL53L0X laser distance sensor
    • the MLX90614 infrared thermometer
    • the old BMP085 pressure sensor
    • the RAK12035 soil moisture sensor
  • Radio library: the tone output is missing.
  • RX8130CE clock chip: times are converted without the time zone functions of the C library.
  • Unified image (one image for all boards): no display driver any more, the button stays.

Today it also carries:

  • code that bridges gaps of normal repeaters (flooded offers at most once a day, data along paths)
  • the operator commands over LoRa
  • the release package
  • the hardening after the external review
  • the protection against replayed remote commands
  • signed offers

The test helper fuota hang is no longer in it. On 20 October 2026 that was 270,080 B, 66 pages and 37,036 B RAM measured. Since then 64 B came in for the Stage-0 abort.

Because less inlined code moves along, patches are 18 to 39 % smaller measured. We built the release tags on the stock FakeTec, once with -Ofast, once with -Os. Every patch passed a round trip: apply it, then check the new image. Both values are in the table above.

One image for all boards

One image for all supported boards means one campaign for the whole area. With one image per model:

  • Every model would need its own campaign with its own patch.
  • A node could only pull from nodes of the same model.
  • The data packets would multiply with the number of models.

Ausfall und Wartezeit

Downtime and waiting

Ausfallzeit beim Anwenden

Das Anwenden dauert rund 1 min. Es sind 12 s bauen, 30 bis 39 s tauschen, dazu der Start. Bei sofortigem Anwenden fehlt der Knoten so lange als Anbieter. Im Testaufbau kostete das den nächsten Hop 56 s gemessen.

Wartezeit auf ein Angebot

Das Angebots-Intervall springt auf 10 s zurück im Code geprüft. Das passiert, wenn das Manifest geprüft oder der Patch vollständig ist. Ebenso, wenn ein Pull weitergeht oder das Anbieten startet, etwa nach einem Neustart. Danach verdoppelt es sich bis auf 2 Tage im Code geprüft. Diesen Zeitgeber nennt man Trickle (mehr dazu auf der Seite Funk).

Das Angebot liegt in der zweiten Hälfte des Intervalls. Wer später dazukommt, hört darum spätestens nach rund 3 Tagen ein Angebot im Code geprüft. Im Leerlauf lagen im Testaufbau 877 s zwischen zwei Angeboten gemessen. Das ist gewollt: Updates dürfen Tage dauern. Im Leerlauf bietet ein Knoten nur einmal je Intervall an.

Downtime while applying

Applying takes about 1 min. That is 12 s build, 30 to 39 s swap, plus the start. With immediate apply the node is missing as a provider for that long. On the bench this cost the next hop 56 s measured.

Waiting for an offer

The offer interval jumps back to 10 s checked in the code. This happens when the manifest is checked or the patch is complete. It also happens when a pull resumes or offering starts, for instance after a reboot. It then doubles up to 2 days checked in the code. This timer is called Trickle (more on the On air page).

The offer falls in the second half of the interval. A node that joins later therefore hears an offer within about 3 days checked in the code. On the bench 877 s passed between two offers when idle measured. This is intended: updates may take days. When idle, a node offers only once per interval.
