Firmware-Updates über LoRa, ohne das Mesh zu belasten

Viele Repeater stehen auf Dächern, Masten und Bergen. Hin kommst du per Leiter, Wanderung oder einer Kletterei, die damals eine gute Idee schien. Ein Update heißt heute: hinfahren. Mit FUOTA geben sich die Repeater neue Firmware selbst über LoRa weiter. Ein kleines Release braucht 60 Datenpakete an einen Nachbarn berechnet, und Update-Daten fluten nie.

Firmware updates over LoRa, without straining the mesh

Many repeaters sit on roofs, masts and mountains. You reach them by ladder, hike or a climb that seemed fine at the time. Today an update means going there. With FUOTA the repeaters pass new firmware to each other over LoRa. A small release takes 60 data packets to one neighbour calculated, and update data never floods.

So funktioniert es

  1. Ein Release wird signiertDer Release-Schlüssel signiert jedes Release offline. Ohne diese Signatur installiert kein Repeater etwas. Heute signiert der Test-Schlüssel, einen Release-Schlüssel gibt es noch nicht offen.
  2. Ein Betreiber installiert esEin Betreiber installiert das neueste signierte Release-Paket per USB oder BLE-OTA auf seinen Repeater. Dieser Repeater ist dann der Seed: Er bietet das Update seinen direkten Nachbarn an.
  3. Nachbarn geben es weiterEin Nachbar holt nur den Patch, Seite für Seite über LoRa, und bietet ihn danach selbst an. Jeder Repeater sendet dafür höchstens 0,3 % der Zeit, rund 11 s je Stunde berechnet. Fällige Mesh-Pakete gehen in der Sendewarteschlange vor.
  4. Jeder Repeater prüft und installiertJede 4-KB-Seite wird gegen das signierte Manifest geprüft, bevor sie weitergeht. Ab Werk wendet ein Repeater das Update nach 7 Tagen an im Code geprüft. Startet die neue Firmware nicht, läuft nach 3 Fehlstarts wieder die alte gemessen.

Such die Fehler

Das ist ein Entwurf, nichts davon ist in MeshCore. Wir legen ihn offen, damit du Denkfehler findest, bevor jemand darauf baut. Am meisten hilft dein Hinweis so: welche Stelle, warum es dort bricht, und wenn möglich ein Szenario oder eine Zahl.

  • Gibt es Topologien oder Zustände, in denen ein Update dauerhaft hängen bleibt, obwohl Teilnehmer verbunden sind?
  • Kann ein Angreifer ohne Release-Schlüssel mehr als verlangsamen? Wo sind wir zu optimistisch?
  • Reicht „Hauptschleife läuft 60 s“ als Gesundheitsprüfung, oder was sollte eine neue Firmware vor der Bestätigung beweisen?

Alle Fragen stehen unter Worum wir dich bitten. So antwortest du: Markiere eine Stelle auf einer Seite. Dann kopierst du sie mit Link, etwa für Discord, oder öffnest gleich ein GitHub-Issue mit dem Zitat. Oder geh direkt zu den Issues im Repository.

How it works

  1. A release is signedThe release key signs every release offline. Without that signature no repeater installs anything. Today the test key signs, no release key exists yet open.
  2. One operator installs itAn operator installs the latest signed release package on their repeater by USB or BLE OTA. That repeater is then the seed: it offers the update to its direct neighbours.
  3. Neighbours pass it onA neighbour pulls only the patch, page by page over LoRa, and then offers it on. Each repeater sends at most 0.3 % of the time for this, about 11 s per hour calculated. Due mesh packets go first in the transmit queue.
  4. Each repeater checks and installsEvery 4 KB page is checked against the signed manifest before it travels on. By default a repeater applies the update after 7 days checked in the code. If the new firmware does not start, the old one runs again after 3 failed boots measured.

Find the flaws

This is a draft, none of it is in MeshCore. We lay it open so that you find the design errors before anyone builds on it. Your note helps most in this form: which passage, why it breaks there, and where possible a scenario or a number.

  • Are there topologies or states in which an update gets stuck for good although participants are connected?
  • Can an attacker without the release key do more than slow things down? Where are we too optimistic?
  • Is "main loop runs for 60 s" enough as a health check, or what should a new firmware prove before confirming?

All questions are under What we ask of you. To respond: select a passage on any page. Then copy it with a link, for Discord for instance, or open a GitHub issue with the quote. Or go straight to the issues in the repository.
