Nur signierte Firmware, und bei einem Fehlstart die alte

Dein Repeater installiert nur, was der Release-Schlüssel signiert hat. Startet die neue Firmware nicht, läuft nach bis zu 3 Probestarts (Startversuchen) wieder die alte gemessen. Im Proof of Concept signiert der Test-Schlüssel, einen Release-Schlüssel gibt es noch nicht offen.

Only signed firmware, and the old one after a failed start

Your repeater installs only what the release key has signed. When the new firmware fails to start in up to 3 test boots, the old one runs again measured. In the proof of concept the test key signs. There is no release key yet open.

Warum es funktioniert

Der Release-Schlüssel signiert das Manifest, die Liste dessen, was zu einem Update gehört. Dazu trägt er ein Zertifikat des Wurzel-Schlüssels, den jedes Image fest enthält im Code geprüft. Das Manifest legt fest:

  • SHA-256 von Quell-Image, neuem Image und Patch
  • einen 8-Byte-Hash je 4-KB-Seite des Patches

Der Patch (Delta-Patch) ist nur der Unterschied zwischen Quell-Image und neuem Image.

Why it works

The release key signs the manifest, the list of everything that belongs to an update. It also carries a certificate of the root key, which every image contains checked in the code. The manifest fixes:

  • the SHA-256 of source image, new image and patch
  • an 8-byte hash per 4 KB page of the patch

The patch (delta patch) is only the difference between source image and new image.

Nur Signiertes wird installiert

Der Knoten prüft in dieser Reihenfolge:

  1. Vor dem Anwenden: der ganze Patch gemessen
  2. Nach dem Bauen: das neue Image gemessen
  3. Vor dem Tausch: beide Slots, durch Stage-0
  4. Nach dem Tausch: Slot A noch einmal

Stage-0 ist der Lader, der beim Start die Images tauscht. Slot A hält die laufende Firmware. Slot B ist das Zwischenlager für das neue Image. Das Layout steht unter Wo was im Flash liegt.

Um anderes zu installieren, müsste ein Angreifer Ed25519 fälschen. Oder er müsste eine zweite Eingabe mit gleichem SHA-256 finden.

Fehler bleiben lokal

Der Knoten prüft jede Seite, bevor er sie weitergibt. Ein verfälschtes Fragment verdirbt darum höchstens die Seite eines einzelnen Empfängers. Der Empfänger holt sie neu gemessen. Ein Fragment ist der Teil von Patch oder Manifest, den ein Datenpaket trägt.

Der Knoten beschreibt ein Wort im Flash höchstens einmal. Steht dort schon ein anderer Wert, löscht der Knoten die ungeprüfte Seite. Eine geprüfte Seite schützt sich selbst.

Ein Manifest sammelt der Knoten zuerst im RAM. In den Flash schreibt er es erst, wenn Hash und Signatur stimmen im Code geprüft. Gefälschte Manifest-Pakete nutzen den Flash so nicht ab.

Fuzzing füttert den Code mit zufällig veränderten Eingaben. Es lief auf dem Rechner mit zusammen 2,8 Milliarden Eingaben (Stand 27. Oktober 2026). Rund 514 Millionen gingen an den Code, der Manifeste, Tickets, Widerrufe und Datenpakete einliest. Der Code im Knoten, der Funkpakete verarbeitet, bekam rund 8,5 Millionen.

Gut 2,1 Milliarden prüften den Filter für Admin-Befehle und die Board-Auswahl. Die übrigen 171 Millionen gingen an Journal, Prüfsumme, Stage-0 und das Anwenden von Patches. Es gab keinen Speicherfehler, also keinen Zugriff außerhalb des erlaubten Speichers, und keinen Absturz gemessen.

Nicht geprüft sind der Code seit diesem Stand und der Teil von MeshCore ohne FUOTA.

Das Update kommt überall an, wo Repeater mit FUOTA verbunden sind

  • Ein Knoten fragt nach dem niedrigsten fehlenden Block, solange ein Nachbar anbietet.
  • Trickle, der Zeitgeber der Angebote, lässt jeden Knoten spätestens nach rund 3 Tagen wieder ein Angebot hören im Code geprüft. Das Intervall wächst bis 2 Tage, das Angebot liegt in seiner zweiten Hälfte.
  • Ab 1 h Intervall bietet jeder Anbieter an, auch wenn er ein gleiches gehört hat.
  • Ein Hop braucht nur einen einzigen Nachbarn mit der Seite. Ein Hop ist ein Sprung von Knoten zu Knoten.
  • Sind alle Repeater mit FUOTA vom Seed aus verbunden, erreicht das Update jeden. Ein Seed ist per USB oder BLE installiert und gibt das Update weiter.
  • Ein unterbrochener Pull (das Holen eines Updates) behält seine geprüften Seiten gemessen.

Update-Daten fluten nie

Update-Daten gehen an direkte Nachbarn. Jeder Knoten sendet höchstens sein Airtime-Budget, seine erlaubte Sendezeit. Die gesamte Last hat damit eine Obergrenze: Zahl der Sender × Budget. Wie viele Knoten mitmachen, ändert daran nichts. Eine Anfrage nennt genau einen Anbieter und löst keine Kettenreaktion aus.

Ausnahmen gibt es nur für Knoten hinter Repeatern ohne FUOTA:

  • Flut-Angebot. Ein Knoten mit einer ganzen Kampagne flutet sein Angebot als Gruppen-Daten in seiner Standard-Region. Eine Region ist der Flood-Scope, auf dem eine Nachricht läuft. Ohne Standard-Region flutet er nicht. Jeder Repeater der Region sendet die Flut einmal weiter.
  • Grenzen der Flut. Er flutet höchstens einmal am Tag je Kampagne. Das tut er nur, wenn er an dem Tag keine Flut dieser Kampagne gehört hat. Dazu muss eines zutreffen:
    • Es ist die erste Woche, nachdem die Kampagne bei ihm vollständig ist. Das sind höchstens 7 eigene Fluten, über Neustarts gezählt.
    • Es ist höchstens eine Woche her, dass er eine Anfrage nach der Kampagne gehört hat.
  • Anfrage und Daten per Pfad. Für einen solchen Knoten laufen Anfrage und Daten als Direct-Pakete entlang eines Pfads. Ein Direct-Paket folgt einem Pfad, der im Paket steht. Sie zählen im Budget des Senders so oft, wie das Paket im Mesh gesendet wird.

Beleg:

  • Mit einem normalen Repeater als Relais gemessen.
  • Auch die Grenzen für frische Fluten und für Fluten nach einer Anfrage gemessen. Der Test-Build lief mit 300 s und 2 Fluten.

Mehr dazu: Wer was weitergibt.

Ein Update kann nicht halb installiert sein

  • Nur Stage-0 ersetzt die laufende Firmware, Seite für Seite, mit Journal. Das Journal ist ein Protokoll der Tauschschritte im Flash.
  • Nach einem Stromausfall setzt Stage-0 genau dort fort.
  • Startet die neue Firmware in 3 Probestarts nicht sauber, tauscht Stage-0 zurück (Rückfall) gemessen. Endet ein Probestart mit Absturz oder Watchdog-Neustart, ist das ein Fehlstart. Das Image ist dann gesperrt im Code geprüft.
  • Fiel in den Probestarts nur der Strom aus, hält der Knoten den automatischen Start zurück, bis er einen Tag ohne Neustart lief (fuota apply wartet nicht). Erst der 3. solche Rückfall sperrt das Image im Code geprüft. Ein Probestart ist jeder Start der neuen Firmware, bevor sie bestätigt ist. Am Testaufbau ist dieser Fall noch nicht gemessen offen.
  • Von selbst wendet ein Knoten ein Update höchstens 3-mal je 24 h Laufzeit an im Code geprüft. So endet eine Schleife aus Anwenden und Neustart. Am Testaufbau galten 600 s statt 24 h. Den 4. Start hielt der Knoten an gemessen. Der Befehl fuota apply zählt nicht mit gemessen.
  • Hat der Knoten Stage-0 den Tausch-Auftrag gegeben, verarbeitet er keine Pakete mehr im Code geprüft. Ein Datenpaket kurz vor dem Neustart ändert das neue Image so nicht.

Beleg: Im Simulator liefen 4.651 Szenarien, alle ohne Fehler, jetzt auch mit dem Weg zurück gemessen. Am Gerät kamen 82 zufällige Watchdog-Resets mitten im Tausch. Ein Watchdog-Reset ist ein Neustart durch den Hardware-Watchdog. Beide Slots waren jedes Mal bitgenau gemessen.

Die Grenzen dieser Argumente

  • Zwei Schlüsselebenen. Ein Wurzel-Schlüssel und eine Ersatz-Wurzel stehen fest im Image.
    • Der Release-Schlüssel signiert die Releases und trägt ein Zertifikat der Wurzel. Wird er gestohlen, widerrufst du ihn: Die Grenze für Zertifikat-Nummern steigt, auch über Funk im Code geprüft.
    • Ein Notfall-Zertifikat und ein Wurzelwechsel durch die Ersatz-Wurzel sind gebaut im Code geprüft. Alles lief nur am Rechner. Am Testaufbau ist es noch nicht gemessen offen. Ein Dieb der Wurzel kann Schlüssel mit neuen Nummern ausstellen, bis die Ersatz-Wurzel gewechselt hat.
    • Dauerfunk (ständiger Funkverkehr) kann den Widerruf verzögern. Gehen beide Wurzeln verloren, erreichst du Knoten nur noch per USB. Das folgt aus der Schlüsselkette im Code, ein eigener Test fehlt. Auch ein signierter Build kann schlecht sein. Eine echte Wurzel und einen echten Release-Schlüssel gibt es noch nicht offen.
  • Die Build-Umgebung. Vor dem Signieren bauen wir zweimal unabhängig und vergleichen das Ergebnis.
    • Am 27. Oktober 2026 waren alle 15 Build-Dateien beider Builds byte-gleich gemessen. SHA-256 legt jedes Software-Paket des Builds fest: 118 Einträge, und 88 frisch geladene Pakete stimmten mit ihnen überein gemessen.
    • Beide Läufe liefen in Containern (abgeschotteten Bauumgebungen). Der zweite lief aber ohne unser Dockerfile (die Bauanleitung des Containers). Ein Release braucht außerdem ein signiertes Tag (eine signierte Versionsmarke in Git) und eine fortlaufende Build-Nummer im Code geprüft. Offen: Der Vergleich zwischen zwei Prozessor-Architekturen fehlt offen.
    • Wer Docker (die Software für den Build-Container) nutzen oder im Checkout (der Kopie des Quellcodes) schreiben darf, beeinflusst den Build. Ein Paket, das in beiden Umgebungen gleich vergiftet ist, fällt nicht auf. Docker und Python auf dem Bau-Rechner sowie das Debian-Paket git im Container-Abbild sind nicht per Hash festgelegt. Ebenso die Python-Pakete (pip) des zweiten Laufs.
    • Code der Build-Plattform läuft aber schon vor dieser Prüfung offen.
  • „Gesund“ heißt:
    • Die Hauptschleife lief im Probestart 60 s. Dazu hat die neue Firmware ein gültiges Paket empfangen und eines gesendet im Code geprüft.
    • Fehlt dieses Lebenszeichen, startet sie neu. Nach 3 solchen Starts tauscht Stage-0 zurück im Code geprüft. Das Image bleibt erlaubt. Der automatische Start folgt frühestens nach 1 Tag, mit wachsendem Abstand (1, 2, 4, 8, 16, dann 30 Tage) im Code geprüft. fuota apply wartet nicht.
    • Am Testaufbau bestätigte ein Knoten so ein Update gemessen. Am Testaufbau fiel ein Knoten ohne Lebenszeichen nach 3 Probestarts zurück. Das Image blieb erlaubt, dieselbe Kampagne ließ sich neu laden gemessen. Offen ist der Rückfall bei einer echten Funklücke im Feld offen.
  • Stromausfall beim überlappenden Anwenden: Hat danach kein Nachbar den Patch, bleibt der Knoten auf der alten Version im Code geprüft. Er wartet auf einen Anbieter in Reichweite. Das Update legt ihn nicht lahm im Code geprüft.
  • Admin-Zugang. Ein Release-Image hat kein Admin-Passwort.
    • Du setzt es per USB mit password im Code geprüft. Wer schon als Admin in der Zugriffsliste (ACL) steht, bleibt aber Admin im Code geprüft.
    • Lief dein Knoten vorher mit Stock und „password“, prüfe die Liste per USB mit get acl. Der Knoten speichert die Einstellungen jetzt über eine Temp-Datei (eine Zwischendatei) und benennt sie danach um. So bleibt die alte Datei bis zum Schluss ganz im Code geprüft.
    • Das gilt auf den Prozessoren nRF52 und STM32. Der nRF52 schreibt im Flash aber immer eine ganze Seite. Ob ein Stromausfall mitten im Speichern wirklich nichts zerstört, ist am Testaufbau noch nicht gemessen offen.
    • ESP32 und RP2040 speichern wie bisher. Fehlt das Passwort nach einem Ausfall, setzt du es per USB neu.
  • Wege, die nur USB heilt. Stürzt eine bestätigte neue Firmware immer wieder ab, tauscht der Knoten von selbst zurück, im Simulator gemessen.
    • Meldet die Firmware einen Fehler an Funk oder Board, startet sie nach 1, 2, 5 und 15 Minuten neu, danach stündlich. Ein Watchdog läuft immer im Code geprüft.
    • Das heilt nicht alles. Abstürze im Abstand von 5 bis 60 Minuten zählen nicht als Fehlstart. Hat Slot A keinen gültigen Start, hilft nur der Bootloader per USB.
    • Ein Doppel-Reset (zwei Neustarts kurz nacheinander) öffnet den UF2-Modus ohne Zeitlimit. In diesem Modus nimmt der Knoten per USB ein Image an. Ein volles Journal stoppt den Knoten. Im Simulator trat das nie auf. Stage-0 lässt sich über Funk nicht ändern im Code geprüft.
    • Am Testaufbau sind diese Fixes noch nicht gemessen offen.
  • Befehle über Funk. Ein Admin-Befehl zählt nur, wenn die Zeit des Absenders höchstens 2 Tage nach der Knotenuhr liegt. Das gilt, sobald die Uhr plausibel ist im Code geprüft. So sperrt eine falsche Uhr in der App den Knoten nicht. Der Befehl fuota cmdtime hebt eine Sperre auf, auch über Funk im Code geprüft. Ohne plausible Knotenuhr greift die Grenze nicht. Am Testaufbau ist das noch nicht gemessen offen.
  • Mehr als 3 Knoten und echte Distanzen sind noch nicht gemessen offen.
  • Stage-0 prüft keine Signatur. Es vertraut dem Auftrag der App offen.

Alle offenen Punkte stehen unter Was noch offen ist.

Only signed material is installed

The node checks in this order:

  1. Before applying: the whole patch measured
  2. After building: the new image measured
  3. Before the swap: both slots, by Stage-0
  4. After the swap: slot A once more

Stage-0 is the loader that swaps the images at boot. Slot A holds the running firmware. Slot B is the intermediate store for the new image. The layout is described under Where everything sits in flash.

To get anything else installed, an attacker would have to forge Ed25519. Or they would have to find a second input with the same SHA-256.

Errors stay local

The node checks every page before it passes the page on. A corrupted fragment can therefore spoil at most the page of a single receiver. That receiver pulls the page again measured. A fragment is the part of a patch or manifest that one data packet carries.

The node writes a word in flash at most once. If a different value is already there, the node erases the unchecked page. A checked page protects itself.

The node first collects a manifest in RAM. It writes it to flash only when hash and signature match checked in the code. Forged manifest packets therefore do not wear out the flash.

Fuzzing feeds the code with randomly altered inputs. It ran on a computer: 2.8 billion inputs in total (state of 27 October 2026). About 514 million went to the code that reads manifests, tickets, retracts and data packets. The code in the node that handles radio packets got about 8.5 million.

Just over 2.1 billion tested the filter for admin commands and the board choice. The other 171 million went to the journal, the checksum, Stage-0 and applying patches. There was no memory error (no access outside the allowed memory) and no crash measured.

Not covered: code added since then and the part of MeshCore without FUOTA.

The update arrives wherever repeaters with FUOTA are connected

  • A node keeps asking for the lowest missing block as long as a neighbour offers.
  • Trickle is the timer of the offers. It makes every node hear an offer again within about 3 days checked in the code. The interval grows up to 2 days, and the offer falls in its second half.
  • From a 1 h interval on, every provider offers, even after hearing an equal offer.
  • One hop needs only a single neighbour with the page. A hop is one jump from node to node.
  • If the repeaters with FUOTA are connected from the seed, the update reaches each one. A seed is installed by USB or BLE and passes the update on.
  • An interrupted pull (fetching an update) keeps its checked pages measured.

Update data never floods

Update data goes to direct neighbours. Every node sends at most its airtime budget, its allowed time on air. The total load therefore has an upper bound: number of senders × budget. How many nodes take part does not change that. A request names exactly one provider, so it triggers no chain reaction.

Exceptions exist only for nodes behind repeaters without FUOTA:

  • Flooded offer. A node with a whole campaign floods its offer. It sends it as group data in its default region. A region is the flood scope a message travels on. Without a default region the node does not flood. Every repeater of the region repeats the flood once.
  • Limits of the flood. The node floods at most once a day per campaign. It does so only if it heard no flood of that campaign that day. One more condition must hold:
    • It is the first week after the campaign became complete there. That is at most 7 floods of its own, counted across reboots.
    • It is at most a week since the node heard a request for the campaign.
  • Request and data along a path. For such a node, request and data travel as direct packets along a path. A direct packet follows a path that is written in the packet. Every transmission of the packet in the mesh counts in the sender's budget.

Evidence:

  • With a normal repeater as relay measured.
  • The limits for fresh floods and for floods after a request hold as well measured. The test build ran with 300 s and 2 floods.

More: Who passes on what.

An update cannot be half-installed

  • Only Stage-0 replaces the running firmware, page by page, with a journal. The journal is a log of the swap steps in flash.
  • After a power loss Stage-0 resumes exactly where it stopped.
  • If the new firmware does not start cleanly, Stage-0 reverts after 3 failed test boots measured. A test boot that ends in a crash or watchdog restart is a failed boot. The image is then blocked checked in the code.
  • If only power failed in the test boots, the node holds back the automatic start. It waits for a day without a restart (fuota apply does not wait). Only the 3rd such revert bans the image checked in the code. A test boot is every start of the new firmware before it is confirmed. This case is not measured on the bench yet open.
  • On its own, a node applies an update at most 3 times per 24 h of running time checked in the code. So a loop of applying and restarting ends. On the bench we used 600 s instead of 24 h. The node stopped the 4th start measured. The command fuota apply does not count measured.
  • Once the node has given Stage-0 the swap job, it handles no more packets checked in the code. So a data packet just before the restart cannot change the new image.

Evidence: The simulator ran 4,651 scenarios without a failure, now including the way back measured. On the device, 82 random watchdog resets hit the middle of the swap. A watchdog reset is a restart by the hardware watchdog. Both slots were bit-exact every time measured.

The limits of these arguments

  • Two key levels. A root key and a backup root are fixed in the image.
    • The release key signs the releases and carries a certificate of the root. If it is stolen, you revoke it: the limit for certificate numbers rises, also over the air checked in the code.
    • An emergency certificate and a root change by the backup root are built checked in the code. All of it ran only on a computer. It is not measured on the bench yet open.
    • A thief of the root can issue keys with new numbers until the backup root has switched. Constant radio traffic can delay the revocation. If both roots are lost, you reach nodes only over USB. This follows from the key chain in the code; there is no test of its own.
    • A signed build can also be bad. There is no real root and no real release key yet open.
  • The build environment. Before signing, we build twice independently and compare the result.
    • On 27 October 2026 all 15 build files of both builds were byte-identical measured. SHA-256 fixes every software package of the build: 118 entries, and 88 freshly downloaded packages matched them measured.
    • Both runs happened in containers (sealed build environments). The second one ran without our Dockerfile (the build recipe of the container). A release also needs a signed tag (a signed version mark in Git) and a running build number checked in the code. Missing: the comparison between two processor architectures open.
    • Whoever may use Docker (the software behind the build container) influences the build. So does whoever may write in the checkout (the copy of the source code). A package poisoned the same way in both environments goes unnoticed. Docker and Python on the build computer are not fixed by a hash. Neither is the Debian package git in the container image. Nor are the Python packages (pip) of the second run.
    • Code of the build platform still runs before this check open.
  • “Healthy” means:
    • the main loop ran for 60 s in the test boot. The new firmware also received a valid packet and sent one checked in the code.
    • Without this sign of life it restarts. After 3 such starts Stage-0 swaps back checked in the code. The image stays allowed. The automatic start waits at least 1 day. The gap then grows: 1, 2, 4, 8, 16, then 30 days checked in the code. fuota apply does not wait.
    • On the bench a node confirmed an update this way measured. On the bench a node reverted after 3 test boots without a sign of life. The image stayed allowed, and the same campaign loaded again measured. Open: the revert in a real radio gap in the field open.
  • Power loss during overlapping apply: if no neighbour has the patch afterwards, the node stays on the old version checked in the code. It waits for a provider in range. The update does not brick it checked in the code.
  • Admin access. A release image has no admin password.
    • You set it over USB with password checked in the code. Whoever is already an admin in the access list (ACL) still stays an admin checked in the code.
    • If your node ran stock with “password” before, check the list over USB with get acl. The node now saves its settings through a temporary file and renames it afterwards. So the old file stays whole until the end checked in the code.
    • This holds on the processors nRF52 and STM32. The nRF52 always writes a whole page in flash, though. Whether a power cut in the middle of saving really destroys nothing is not measured on the bench yet open.
    • ESP32 and RP2040 save as before. If the password is missing after a cut, set it again over USB.
  • Paths only USB cures. If a confirmed new firmware keeps crashing, the node swaps back by itself, in the simulator measured.
    • If the firmware reports a fault of the radio or board, it restarts after 1, 2, 5 and 15 minutes, then hourly. A watchdog always runs checked in the code.
    • This does not cure everything. Crashes 5 to 60 minutes apart do not count as a failed start. If slot A has no valid start, only the bootloader over USB helps.
    • A double reset (two restarts in quick succession) opens the UF2 mode without a time limit. In this mode the node accepts an image over USB. A full journal stops the node. It never happened in the simulator. Stage-0 cannot be changed over the air checked in the code.
    • These fixes are not measured on the bench yet open.
  • Commands over the air. An admin command counts only when the time of the sender is at most 2 days ahead of the node clock. This holds once that clock is plausible checked in the code. So a wrong clock in the app cannot lock the node. The command fuota cmdtime lifts a lock, also over the air checked in the code. Without a plausible node clock the limit does not apply. This is not measured on the bench yet open.
  • More than 3 nodes and real distances are not measured yet open.
  • Stage-0 checks no signature. It trusts the job from the app open.

Angriffe im Detail

Attacks in detail

Wie sicher ist das?

Über Funk installiert ein Knoten nur, was der Release-Schlüssel signiert hat. Wer am Gerät ist, kann jedes Image installieren: Stage-0, UF2, serielles DFU und BLE-DFU prüfen keine Signatur. Ein Angreifer erreicht einen Knoten auch über mehrere Hops. Dafür nutzt er Pfade über normale Repeater oder geflutete Angebote in einer Region.

Er kann ein Update verlangsamen, für Knoten hinter normalen Repeatern auch verhindern, und Airtime verbrauchen. Das geht höchstens bis zum Budget der erreichten Knoten. Mit gefälschten Angeboten, falschen Größen oder fremden Schlüsseln nimmt er keinem Knoten die geprüfte Kampagne. Er erreicht auch keine Sperre einer echten Kampagne gemessen. Eine Flut unsignierter Anfragen kann das Laden aber aufhalten, während er sendet gemessen. Eine Drossel dagegen gibt es noch nicht offen.

Das schwächste Glied sind die Schlüssel. Wer den Release-Schlüssel hat, darf bis zum Widerruf alles, auch einen Build, der FUOTA abschaltet. Wer die Wurzel hat, kann das ändern, bis die Ersatz-Wurzel wechselt.

How safe is it?

Over the air, a node installs only what the release key signed. Anyone at the device can install any image: Stage-0, UF2, serial DFU and BLE DFU check no signature. An attacker reaches a node also over several hops. The attacker uses paths across normal repeaters or flooded offers in a region.

The attacker can slow an update down, stop it for nodes behind normal repeaters, and use up airtime. That reaches at most the budget of the nodes reached. Forged offers, wrong sizes and foreign keys cannot take a node's checked campaign. Nor can they get a genuine campaign banned measured. A flood of unsigned requests can still hold up loading while the attacker sends measured. A throttle against this does not exist yet open.

The weakest link is the keys. Whoever has the release key may do anything until it is revoked, including a build that switches FUOTA off. Whoever has the root can change that until the backup root has switched.

Annahme. Ein Angreifer erreicht den Knoten auf einem dieser Wege:

  • in Funkreichweite des Knotens
  • über einen Pfad zu ihm: Jeder Repeater leitet Direct-Pakete mit Pfad weiter, auch FUOTA-Pakete
  • in derselben Region: Ein geflutetes Angebot erreicht die ganze Region. Der Schlüssel des FUOTA-Kanals folgt aus einem festen Namen

Der Angreifer kann:

  • beliebige Pakete senden
  • fremde Pakete mitschneiden und wiederholen
  • jede Absender-Kennung vortäuschen
  • eigene Knoten mit veränderter Firmware betreiben

Er hat den Release-Schlüssel nicht und keinen physischen Zugang zu fremden Knoten.

Begriffe in der Tabelle:

  • Ticket. Der Teil des Angebots mit Ziel, Build, Patch-Größe, Quelle, Manifest-Hash und der Signatur des Release-Schlüssels.
  • Stock. MeshCore wie veröffentlicht, unverändert.

Assumption. An attacker reaches the node in one of these ways:

  • within radio range of the node
  • over a path to it. Every repeater forwards direct packets with a path, FUOTA packets too
  • in the same region: a flooded offer reaches the whole region. The key of the FUOTA channel follows from a fixed name

The attacker can:

  • send arbitrary packets
  • record foreign packets and replay them
  • fake any sender ID
  • run their own nodes with modified firmware

The attacker has neither the release key nor physical access to foreign nodes.

Terms in the table:

  • Ticket. The part of the offer that carries the signature of the release key. It also holds target, build, patch size, source and manifest hash.
  • Stock. MeshCore as published, unchanged.

Echte Fragmente verfälschenDer Seiten-Hash schlägt an, und der Knoten holt die Seite neu.Verzögerung. Wer schneller fälscht, als echte Quellen senden, kann einen Knoten aufhalten (Dienstverweigerung, DoS).gemessen
Altes echtes Manifest wiederholenDer Build ist nicht höher als der laufende, der Knoten lehnt das Manifest ab.Keinergemessen
Echtes, hier schon gescheitertes Update wiederholenDer Knoten lehnt es ab, bevor er ein Fragment anfragt. Das gilt auch, wenn danach ein anderes Update kam. Eine dauerhafte Liste hält die letzten 4 gescheiterten Images.Erst ab dem 5. gescheiterten Image fällt das älteste heraus.gemessen
Gefälschter Retract (signierter Rückruf)Die Signatur ist falsch, der Knoten verwirft den Retract.Keinergemessen
Echten Retract wiederholenEr bleibt ohne neue Wirkung: Der Knoten kennt ihn schon.Keiner, ein Retract ist ohnehin endgültigim Code geprüft
Alte Retracts wiederholen, bis der Speicher voll istDer Knoten speichert keinen Retract für einen Build unter dem laufenden. Ist der Speicher voll, verwirft er den Retract mit dem niedrigsten Build.Erst ab dem 5. Retract fällt der für den niedrigsten Build heraus.gemessen: 4 Plätze, ein 5. Retract verdrängte den niedrigsten Build
Alten Fern-Befehl eines Admins nach einem Neustart wiederholenStock hält den Zeitstempel eines Admins nur im RAM. FUOTA speichert den Zeitstempel des letzten ändernden Fern-Befehls. Das gilt für auto, apply, reboot, clkreboot, poweroff, shutdown und start ota. Gleiche und ältere Zeitstempel lehnt es ab. Der Befehl fuota apply verlangt dazu die Build-Nummer.Keiner, außer einem nie zugestellten, mitgeschnittenen neueren Befehl.gemessen
Sich mit dem Werkspasswort als Admin anmeldenEin Release-Image liefert kein Admin-Passwort aus. Im Release öffnen weder ein leeres Passwort noch „password“ einen Admin-Login. Das eigene Passwort setzt der Betreiber per USB. In Test-Builds mit „password“ führt der Knoten start ota, fuota auto und fuota apply über das Mesh nicht aus.Keiner über das Passwort. Wer schon als Admin in der Zugriffsliste (ACL) des Knotens steht, bleibt Admin, auch nach dem Wechsel auf das Release.gemessen: Test am Rechner für Login und Befehlsprüfung
Einen Fern-Befehl mit einem Zeitstempel weit in der Zukunft sendenDas braucht das Admin-Passwort. Liegt der Zeitstempel mehr als 2 Tage nach der Uhr des Knotens, lehnt er ab und speichert ihn nicht. Kennt der Knoten noch keine plausible Uhrzeit, setzt der Admin den Zähler mit fuota cmdtime über das Mesh zurück.Fern-Befehle des Admins bleiben bis dahin gesperrt. Ein mitgeschnittener Befehl aus der Zukunft kann danach erneut sperren.gemessen: Test am Rechner; am Testaufbau offen
Ein Befehl über das Mesh gibt sich als USB ausDer Knoten wertet einen Befehl nur als USB-Befehl, wenn er über die serielle Schnittstelle kommt. Ein Befehl über das Mesh schaltet die Befehle zum Laden eines Patches nicht frei.Keinergemessen
Billige Anfragen sendenDer genannte Anbieter sendet bis zu 16 Datenpakete je Anfrage, in Airtime rund das 80-Fache bei CR 4/8 und das 64-Fache bei CR 4/5 berechnet. Mit Ziel 0xFFFF sendet jeder Anbieter in Reichweite, über einen Pfad auch aus der Ferne. Der Anbieter bedient reihum ab dem zuletzt gesendeten Datenpaket. Anfragen über Pfade bekommen höchstens die Hälfte seiner Airtime.Anbieter schöpfen ihr Budget aus. Eine echte Anfrage wird reihum bedient gemessen (mit zwei Anfragenden). Eine Flut unsignierter Anfragen kann aber das Laden einer Kampagne aufhalten. Knoten C wurde in 1500 s nicht fertig, Anbieter A sendete 235 statt 46 Datenpakete gemessen. Eine Drossel dagegen gibt es noch nicht offen.gemessen: eine immer wiederholte Anfrage bekommt ihren Anteil, keinen Vorrang
Echtes Angebot eines neueren Builds (auch mitgeschnitten und wiederholt)Der Knoten hält eine Kampagne: Er bedient, wartet aufs Anwenden oder hat den Pull pausiert. Er holt nur das neue Manifest in den RAM. Er wechselt erst, wenn Signatur, Passung, Größe und ein höherer Build stimmen. Sonst behält er seine Kampagne.Nur echte Kampagnen. Ein wiederholtes echtes Angebot mit falscher Seitenzahl oder falschem Absender kann Anfragen ins Leere lenken.gemessen
Angebot mit echter ID und falscher Größe oder falschem Quell-PräfixGröße, Quelle und ID stehen im signierten Ticket. Ein geändertes Feld bricht die Signatur, und der Knoten verwirft das Angebot.Keinergemessen
Aus der Ferne über Pfade und FlutPfade über beliebige Repeater tragen Anfragen und Daten bis zum Ziel. Geflutete Angebote erreichen eine Region.Die Kopien der Repeater zählen in kein Budget. Jeder Knoten verwirft gefälschte Angebote an der Ticket-Signatur.gemessen: gefälschte Angebote. im Code geprüft: geflutete Angebote, dieselbe Prüfung
Echtes Flut-Angebot täglich wiederholenEin Knoten, der die Flut seiner Kampagne gehört hat, flutet an diesem Tag nicht selbst. Knoten hinter normalen Repeatern lernen dann den Pfad zum Angreifer.Wiederholt der Angreifer täglich, fragen diese Knoten ins Leere und bekommen das Update nicht. Ein falsches Image entsteht nie.im Code geprüft
Absender-Kennung fälschenDas betrifft Logs, den Testfilter und die Erkennung eines beschäftigten Anbieters. Ein Knoten hält einen Anbieter nur nach einem richtigen Datenpaket für beschäftigt, höchstens einmal je eigener Anfrage im Code geprüft. Kurze Datenpakete halten ihn nicht auf. Falsche Datenpakete im Namen eines Anbieters bringen den Knoten dazu, ihn zu meiden.Verzögerung: Der Knoten holt dann bei anderen oder bei „wer es hat“.gemessen: Bei einem Strom kurzer Datenpakete sendete der Knoten 8 Anfragen in 180 s. Meiden: gemessen, siehe Nebenslot
Kurze Datenpakete im Namen eines Anbieters sendenEin Knoten will ein Datenpaket senden. Hört er einen Nachbarn dasselbe senden, streicht er seines nur, wenn Länge und Inhalt mit seiner Kopie übereinstimmen.Kein falsches Datenpaket, kein Zustandswechsel. Das Laden dauerte am Testaufbau aber 83 % länger (208 s ohne, 381 s mit Angriff) gemessen. Die Ursache ist nur vermutet offen.gemessen: Der Anbieter verwarf 39 kurze Fälschungen und sendete weiter
Echte Angebote mit ausgedachten Absender-Kennungen wiederholenEin Knoten behält den Nachbarn, der zuletzt geprüfte Datenpakete lieferte, in seiner Anbieterliste und fragt ihn zuerst.Ein mitgeschnittenes echtes Datenpaket unter einer ausgedachten Kennung umgeht das. Der Durchsatz sinkt dann auf rund ein Drittel berechnet.gemessen: Anfragen an eine Fälschung vorher 5, nachher 1
Fremde Anfragen für denselben Block sendenHört ein Knoten eine fremde Anfrage für seinen Block, schiebt er die eigene höchstens einmal je eigener Anfrage auf.Keinerim Code geprüft
Anfragen senden, damit ein Knoten nicht anwendetBeim überlappenden Anwenden wartet ein Knoten, solange Nachbarn den Patch noch anfragen. Anfragen an einen anderen Anbieter zählen nicht. Das Fenster endet spätestens nach 7 Tagen.Verzögerung bis 7 Tage, nur beim überlappenden Anwendenim Code geprüft
Gefälschte Manifest-Pakete senden, um den Flash abzunutzenDer Knoten sammelt ein Manifest im RAM. In den Flash schreibt er nur ein geprüftes.Nicht mehr als bei einem echten Updategemessen: Löschungen im Test am Rechner vorher 96, nachher 5

Eigener Knoten ohne BudgetEr sendet so viel, wie er will, wie jeder Störsender.Betroffen ist der Kanal. Bei anderen Knoten installiert er nichts.installiert nichts: im Code geprüft; Last auf dem Kanal: offen

Offer a manifest signed with an own key, or forge an offerThe signature in the ticket of the offer does not come from the release key. The node drops the offer before it asks for anything. It does so also while it holds a campaign. It ignores offers that do not concern it without checking them.Processing time, no airtime. One check per new ticket takes 17.8 ms measured.measured: also while holding a campaign
Corrupt genuine fragmentsThe page hash fails, and the node pulls the page again.Delay. Whoever forges faster than genuine sources send can stall a node (denial of service, DoS).measured
Replay an old genuine manifestThe build is not higher than the running one, so the node rejects the manifest.Nonemeasured
Replay a genuine update that has already failed hereThe node rejects it before it requests a fragment. It does so also after another update came in between. A persistent list holds the last 4 failed images.Only from the 5th failed image on does the oldest one drop out.measured
Forged retract (signed recall)The signature is wrong, and the node drops the retract.Nonemeasured
Replay a genuine retractIt has no new effect: the node already knows it.None, a retract is final anywaychecked in the code
Replay old retracts until the store is fullThe node stores no retract for a build below the running one. When the store is full, it drops the retract with the lowest build.Only from the 5th retract on does the one for the lowest build fall out.measured: 4 places, a 5th retract pushed out the lowest build
Replay an old remote command of an admin after a rebootStock keeps the timestamp of an admin only in RAM. FUOTA saves the timestamp of the last remote command that changes something. That covers auto, apply, reboot, clkreboot, poweroff, shutdown and start ota. It refuses equal and older timestamps. The command fuota apply also requires the build number.None, except a recorded newer command that was never delivered.measured
Log in as admin with the factory passwordA release image ships no admin password. In a release neither an empty password nor “password” opens an admin login. The operator sets their own password over USB. In test builds with “password” the node does not run start ota, fuota auto and fuota apply over the mesh.None through the password. Whoever is already an admin in the node's access list (ACL) stays an admin, also after the switch to the release.measured: test on a computer for login and command check
Send a remote command with a timestamp far in the futureThis needs the admin password. If the timestamp is more than 2 days ahead of the node's clock, the node refuses it and does not save it. If the node does not know a plausible time yet, the admin resets the counter with fuota cmdtime over the mesh.The admin's remote commands stay blocked until then. A recorded command from the future can block them again afterwards.measured: test on a computer; on the bench open
A command over the mesh poses as USBThe node treats a command as a USB command only when it comes through the serial port. A command over the mesh does not unlock the commands that load a patch.Nonemeasured
Send cheap requestsThe named provider sends up to 16 data packets per request. That is about 80 times the airtime at CR 4/8. At CR 4/5 it is 64 times calculated. With target 0xFFFF every provider in range sends, along a path also from afar. The provider serves in turn from the data packet sent last. Requests along paths get at most half of its airtime.Providers exhaust their budget. A genuine request is served in turn measured (with two requesters). A flood of unsigned requests can still hold up loading. Node C did not finish in 1500 s, and provider A sent 235 data packets instead of 46 measured. A throttle against this does not exist yet open.measured: a request repeated again and again gets its share, not priority
Genuine offer of a newer build (also recorded and replayed)The node holds a campaign: it serves, waits to apply or has paused its pull. It pulls only the new manifest into RAM. It switches only once signature, fit, size and a higher build check out. Otherwise it keeps its campaign.Genuine campaigns only. A replayed genuine offer with wrong pages or a wrong sender can send requests nowhere.measured
Offer with a genuine ID and a wrong size or source prefixSize, source and ID are in the signed ticket. A changed field breaks the signature, and the node drops the offer.Nonemeasured
From afar via paths and floodsPaths across any repeaters carry requests and data to the target. Flooded offers reach a region.The copies of the repeaters count in no budget. Every node drops forged offers at the ticket signature.measured: forged offers. checked in the code: flooded offers, the same check
Replay a genuine flooded offer every dayA node that heard the flood of its campaign does not flood it itself that day. Nodes behind normal repeaters then learn the path to the attacker.If the attacker repeats this daily, these nodes ask into the void and do not get the update. A wrong image never results.checked in the code
Fake the sender IDThis affects logs, the test filter and the detection of a busy provider. A node counts a provider as busy only after a correct data packet, at most once per own request checked in the code. Short data packets do not hold it up. Wrong data packets in a provider's name make the node avoid that provider.A delay: the node then pulls from others or from “whoever has it”.measured: with a stream of short data packets the node sent 8 requests in 180 s. If it hears a neighbour send the same one, it drops its own only when length and content match its copy.No false data packet, no change of state.
