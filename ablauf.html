So kommt ein Update von Repeater zu Repeater

Einer in deiner Gegend installiert das neueste signierte Release-Paket per USB oder BLE-OTA und wird Seed. Seine direkten Nachbarn holen den Patch, prüfen jede Seite und geben sie weiter. Ab Werk wendet dein Repeater das Update nach 7 Tagen an im Code geprüft, auf Befehl auch sofort.

How an update gets from repeater to repeater

Someone in your area installs the latest signed release package by USB or BLE OTA and becomes the seed. Its direct neighbours pull the patch, check every page and pass it on. By default your repeater applies the update after 7 days checked in the code, or at once on command.

Das Prinzip

  1. Seed werden. Einer in deiner Gegend installiert das neueste signierte Release-Paket von GitHub.
    • Das geht per USB oder per BLE-OTA vom Rechner, vom Handy ungetestet.
    • Sein Repeater ist damit der Seed, der erste Knoten mit dem neuen Release.
    • Er bietet das Update seinen direkten Nachbarn an.
  2. Nur den Unterschied holen. Wer das Update braucht, holt den Patch: nur den Unterschied zu seiner Version.
    • Über Funk geht nur dieser Delta-Patch (bsdiff + heatshrink).
    • Der Release-Schlüssel (Ed25519) signiert das Manifest: die Liste aller Teile des Updates mit ihren Prüfsummen. Ohne gültige Signatur passiert nichts.
    • Der Knoten fragt einen Nachbarn an, der das Update angeboten hat. Nur dieser antwortet.
  3. Prüfen, weitergeben, anwenden. Jeder Repeater prüft jede 4-KB-Seite gegen das Manifest.
    • Erst dann gibt er sie weiter, schon während er den Rest holt (Pipelining). Falsche Daten kommen nie weiter als einen Hop (Funksprung).
    • Dein Repeater wendet im A/B-Verfahren an. Slot A hält das laufende Image, Slot B das neue. Der Loader Stage-0 tauscht die Slots beim Start.
    • Startet die neue Firmware nicht, läuft nach 3 Fehlstarts wieder die alte gemessen.

Was in jedem Schritt gilt

  • FUOTA steht für Firmware Update Over the Air. Seine Pakete gehen an direkte Nachbarn, in einem eigenen Pakettyp (0x0E).
  • Kein Knoten leitet ein solches Paket ohne Pfad weiter, auch kein normaler Repeater (ohne FUOTA). MeshCore verwirft unbekannte Typen.
  • Nur hinter normalen Repeatern (ohne FUOTA) laufen Anfrage und Daten auf einem festen Pfad. Ein Angebot flutet dort höchstens einmal am Tag als Gruppen-Nachricht im Code geprüft. Mehr dazu: Wer was weitergibt (früher Abschnitt 6).
  • Update-Daten fluten nie.
  • Jeder Knoten sendet Update-Pakete nur im harten Airtime-Budget (Sendezeit). Ab Werk sind das 0,3 % im Code geprüft.
  • Ein Update darf darum Tage dauern, und der normale Verkehr merkt davon wenig.

The principle

  1. Become the seed. Someone in your area installs the latest signed release package from GitHub.
    • That works by USB or by BLE OTA from a computer, untested from a phone.
    • Their repeater is then the seed, the first node with the new release.
    • It offers the update to its direct neighbours.
  2. Pull only the difference. A node that needs the update pulls the patch: only the difference from its version.
    • Only this delta patch (bsdiff + heatshrink) travels over radio.
    • The release key (Ed25519) signs the manifest. It lists every part of the update with its checksum. Without a valid signature nothing happens.
    • The node asks one neighbour that has offered the update. Only that neighbour answers.
  3. Check, pass on, apply. Every repeater checks each 4 KB page against the manifest.
    • Only then does it pass the page on, even while pulling the rest (pipelining). Wrong data never travels further than one hop (one radio link).
    • Applying uses the A/B method. Slot A holds the running image, slot B the new one. The loader Stage-0 swaps the slots at boot.
    • If the new firmware does not start, the old one runs again after 3 failed boots measured.

What holds in every step

  • FUOTA stands for Firmware Update Over the Air. Its packets go to direct neighbours, in a packet type of their own (0x0E).
  • No node forwards such a packet without a path. That includes a normal repeater (without FUOTA). MeshCore drops unknown types.
  • Only behind normal repeaters (without FUOTA) do request and data travel along a fixed path. An offer floods there at most once a day as a group message checked in the code. More: Who passes on what (formerly section 6).
  • Update data never floods.
  • Every node sends update packets only within a hard airtime budget (time on air). By default that is 0.3 % checked in the code.
  • An update may therefore take days, and normal traffic notices little of it.

How an update runs

The measured times come from the bench (SF7, 10 % budget). In the mesh, SF8 and a 0.3 % budget apply (default). Those times are under Load on the mesh.

Release-Build, offline signiertPatch und Manifest bauen Je Modell und Quell-Version entsteht ein Patch. Das Manifest hat 292 B plus 8 B je 4-KB-Seite, mit Angebots-Ticket im Code geprüft. Es nennt Ziel-Gerät, Build-Nummer, Größen und die SHA-256 von Quell-Image, neuem Image und Patch. Je Seite trägt es die ersten 8 Byte ihrer SHA-256. Dazu kommt ein Flag für das überlappende Anwenden. Dabei überschreibt das neue Image Patch-Seiten, die der Knoten schon gelesen hat. Der Release-Build spielt den Apply-Code des Geräts vorher auf dem Rechner durch. Das Flag setzt er nur, wenn das sicher ist. Am Ende steht das Angebots-Ticket: Ziel, Build, Patch-Größe, Quelle und Hash des Manifests. Jedes Angebot trägt es. Der Release-Schlüssel signiert Manifest und Ticket offline, getrennt vom Build. Die Build-Umgebung hat den privaten Schlüssel nie.
Irgendein Betreiber, per USB oder BLENeuestes Release-Paket installieren Das signierte Release-Paket enthält das neue Image und die Kampagne von der Vorversion. Sie besteht aus Manifest und Patch. Wer es per UF2, seriellem DFU oder BLE installiert, wird Seed. Beim Start prüft die Firmware die Kampagne wie eine geholte und bietet sie an. Alle anderen holen sie per Funk gemessen. Im Paket liegt die Kampagne am Anfang von Slot B. Der UF2-Bootloader schreibt nicht bis ans Ende von Slot B. Darum verschiebt die Firmware sie beim Start dorthin. Mehrere Seeds schaden nicht: Die Kampagne zählt über ihre ID. Am Testaufbau lädt ein USB-Befehl Manifest und Patch auch einzeln.
Jeder Knoten mit geprüftem ManifestAnbieten Das Angebot trägt das signierte Ticket (ID, Größe, Ziel, Build, Quell-Präfix). Dazu nennt es die Zahl geprüfter Seiten. Das Intervall verdoppelt sich von 10 s bis auf 2 Tage im Code geprüft. Der Knoten sendet in der zweiten Hälfte des Intervalls. Hört ein Knoten vorher ein gleiches Angebot, schweigt er (Trickle). Das gilt nur in Intervallen unter 1 h im Code geprüft. Danach bietet jeder Knoten einmal je Intervall an. So bekommt auch ein Nachbar ein Angebot, der die anderen nicht hört.
NachbarAngebot prüfen Er nimmt ein Angebot nur an, wenn Ziel-Gerät und Quell-Präfix passen. Außerdem muss die Build-Nummer höher sein. Das Quell-Präfix sind die ersten 8 Byte der SHA-256 des laufenden Images. Passt ein Angebot nicht, bleibt der Knoten still. Sonst prüft er die Signatur des Tickets. Ein gefälschtes Angebot verwirft er hier. Während eines Probestarts zieht er nicht. Du merkst: Ist das Netz schon aktuell, fließen keine Daten.
NachbarManifest holen Das Manifest kommt in 2 bis 4 Fragmenten. Der Knoten prüft die Signatur (Ed25519 über die CryptoCell), Ziel, Quelle, Build und Platz. Dazu prüft er, ob dieses Update hier schon gescheitert ist. Fällt eine Prüfung durch, holt er kein einziges Patch-Fragment. Nur was signiert ist und hier nie passen kann, sperrt der Knoten über Neustarts. Sonst ruht die Kampagne 10 min im Code geprüft.
NachbarPatch holen Die Anfrage nennt den niedrigsten Block mit Lücken. Der Block hat 16 Fragmente im Code geprüft, eine Bitmap nennt die fehlenden. Sie geht an genau einen Nachbarn, den zuletzt gehörten, dessen Angebot den Block abdeckt. Nur er antwortet. Kommt nichts, nennt die nächste Anfrage einen anderen Anbieter. Kennt der Knoten keinen weiteren, fragt er alle (Kennung 0xFFFF). Ein MeshCore-Schlüssel beginnt nie mit 0xFF. Fragmente landen direkt im Flash.
NachbarJede Seite sofort prüfen Ist eine 4-KB-Seite vollständig, prüft der Knoten sie gegen ihren Hash aus dem Manifest. Falsch: Er löscht die Seite und holt sie neu. Richtig: Er darf sie ab sofort weitergeben.
Derselbe KnotenWeitergeben, während er noch holt Er bietet an, sobald sein Manifest geprüft ist, mit der Zahl geprüfter Seiten. Fragt ein Nachbar nach einer Seite, die er noch nicht hat, merkt er sich das. Sobald die Seite fertig ist, bietet er sofort an.
Derselbe KnotenVollständig: wann er anwendet Ab Werk wendet er an, wenn die Kampagne 7 Tage komplett war im Code geprüft. Dieser Standard heißt fuota auto delay. Die Laufzeit zählt über Neustarts. Ein Retract (signierter Rückruf) in diesen 7 Tagen stoppt das Anwenden. Nach fuota auto off wartet er auf dein fuota apply <build>. Mit fuota auto now wendet er sofort an. Das gilt, wenn der Patch hinter das neue Image passt. Sonst wartet er ein Fenster ab, in dem er weitergibt. Es endet frühestens nach einer Mindestzeit. Dann muss eine Weile niemand nach dem Patch gefragt haben. Zudem darf nichts mehr auszuliefern sein. Die Werte für das Feld sind ein Vorschlag offen. Am Testaufbau sind es 120 s und 180 s im Code geprüft. Du merkst: fuota info zeigt Build, Auto-Apply und den Stand des Updates.
Derselbe KnotenNeues Image in Slot B bauen Der Knoten prüft die SHA-256 über den ganzen Patch. Dann baut er das neue Image in Slot B (12 s gemessen). Er prüft die SHA-256 des Ergebnisses gegen das Manifest. Danach schreibt er den Tausch-Auftrag in die Status-Seite und startet neu.
Stage-0Prüfen, tauschen, Probestart Vor dem Tausch prüft Stage-0 Slot B (neu) und Slot A (alt) gegen den Auftrag. Dabei prüft es Vektortabelle und SHA-256. Dann tauscht es seitenweise, jeder Schritt steht im Journal (30 bis 39 s gemessen). Danach prüft es Slot A erneut gegen den Soll-Hash. Der Probestart läuft mit Watchdog (30 s im Code geprüft). Lehnt Stage-0 einen Auftrag ab, etwa wegen eines unbekannten Auftragsformats, startet die alte Firmware. Das Image ist dann gesperrt wie nach einem Rückfall gemessen.
Neue FirmwareBestätigen oder zurück 60 s gesunde Hauptschleife bestätigen die neue Firmware im Code geprüft. Nach 3 Fehlstarts tauscht Stage-0 zurück (Rückfall) gemessen. Gesperrt ist nur dieses eine Image. Der Knoten installiert es nie wieder und bietet es nicht an. Du merkst: Dein Knoten bleibt nicht alt. Jedes spätere Release mit einem Patch von seinem Stand installiert er normal.
Derselbe KnotenWeiter anbieten Lag der Patch hinter dem neuen Image, liegt er nach dem Tausch noch da. Der Knoten prüft ihn beim Start erneut und bietet weiter an. Nach einem überlappenden Anwenden ist der Patch weg. Der Knoten bietet ihn nicht mehr an.
Release-Schlüssel, jederzeitZurückziehen Ein Retract (80 B im Code geprüft) gilt für ein Ziel und einen Build. Jeder Knoten, der ihn prüft, stoppt Holen und Anbieten und speichert ihn. Er sendet ihn bis zu 3-mal im Code geprüft. Auf ein Angebot dieses Builds antwortet er mit dem Retract, höchstens alle 30 s.
Release build, signed offlineBuild patch and manifest One patch per model and source version. The manifest takes 292 B plus 8 B per 4 KB page checked in the code. That includes the offer ticket. It names target device, build number and sizes. It also holds the SHA-256 of source image, new image and patch. For each page it carries the first 8 bytes of its SHA-256. A flag covers overlapping apply. The new image then overwrites patch pages that the node has already read. Beforehand the release build plays the apply code of the device through on a computer. It sets the flag only if that is safe. The offer ticket comes last: target, build, patch size, source and hash of the manifest. Every offer carries it. The release key signs manifest and ticket offline, separate from the build. The build environment never holds the private key.
Any operator, over USB or BLEInstall the latest release package The signed release package holds the new image and the campaign from the previous version. The campaign is a manifest plus a patch. Whoever installs it over UF2, serial DFU or BLE becomes the seed. At boot the firmware checks the campaign like a pulled one and offers it. All others pull it over the air measured. In the package the campaign sits at the start of slot B. The UF2 bootloader does not write up to the end of slot B. So the firmware moves the campaign to the end at boot. Several seeds do no harm: the campaign counts by its ID. On the bench, a USB command also loads manifest and patch separately.
Every node with a checked manifestOffer The offer carries the signed ticket (ID, size, target, build, source prefix). It also names the number of checked pages. The interval doubles from 10 s up to 2 days checked in the code. The node sends in the second half of the interval. If a node hears an equal offer before that, it stays silent (Trickle). That holds only in intervals below 1 h checked in the code. After that every node offers once per interval. So even a neighbour that cannot hear the others gets an offer.
NeighbourCheck the offer It accepts an offer only if target device and source prefix match. The build number must also be higher. The source prefix is the first 8 bytes of the SHA-256 of the running image. If an offer does not fit, the node stays silent. Otherwise it checks the signature of the ticket. It drops a forged offer here. During a test boot it does not pull. You notice: if the mesh is already up to date, no data flows.
NeighbourPull the manifest The manifest comes in 2 to 4 fragments. The node checks the signature (Ed25519 via the CryptoCell), target, source, build and space. It also checks whether this update has already failed here. If a check fails, it pulls no patch fragment at all. Only what is signed and can never fit here is banned across reboots. Otherwise the campaign rests for 10 min checked in the code.
NeighbourPull the patch The request names the lowest block with missing fragments. The block has 16 fragments checked in the code. A bitmap names the missing ones. It goes to exactly one neighbour, the most recent one whose offer covers the block. Only that one answers. If nothing comes, the next request names another provider. If the node knows no other one, it asks everybody (ID 0xFFFF). A MeshCore key never starts with 0xFF. Fragments go straight to flash.
NeighbourCheck every page at once When a 4 KB page is complete, the node checks its hash against the manifest. Wrong: it erases the page and pulls it again. Right: it may pass the page on from now on.
Same nodePass on while still pulling It offers as soon as its manifest is checked, with the number of checked pages. If a neighbour asks for a page it does not have yet, it remembers that. As soon as the page is complete, it offers at once.
Same nodeComplete: when it applies By default it applies 7 days after the campaign is complete checked in the code. This default is fuota auto delay. The running time counts across reboots. A retract (signed recall) within those 7 days stops the apply. After fuota auto off it waits for your fuota apply <build>. With fuota auto now it applies at once. That holds if the patch fits behind the new image. Otherwise it waits out a window in which it passes the patch on. The window ends no sooner than a minimum time. Then nobody may have asked for the patch for a while. And nothing may be left to deliver. The values for the field are a proposal open. On the bench they are 120 s and 180 s checked in the code. You notice: fuota info shows build, auto apply and the state of the update.
Same nodeBuild the new image in slot B The node checks the SHA-256 over the whole patch. Then it builds the new image in slot B (12 s measured). It checks the SHA-256 of the result against the manifest. After that it writes the swap job into the status page and reboots.
Stage-0Check, swap, test boot Before the swap, Stage-0 checks slot B (new) and slot A (old) against the job. It checks the vector table and the SHA-256. Then it swaps page by page and journals every step (30 to 39 s measured). Afterwards it checks slot A again against the target hash. The test boot runs with a watchdog (30 s checked in the code). If Stage-0 refuses a job, for example an unknown job format, the old firmware starts. The image is then blocked as after a revert measured.
New firmwareConfirm or revert 60 s of a healthy main loop confirm the new firmware checked in the code. After 3 failed boots Stage-0 swaps back (revert) measured. Only this one image is blocked. The node never installs it again and does not offer it. You notice: your node does not stay old. It installs any later release that has a patch from its current version as usual.
Same nodeKeep offering If the patch sat behind the new image, it is still there after the swap. The node checks it again at boot and keeps offering. After an overlapping apply the patch is gone. The node no longer offers it.
Release key, any timeRetract A retract (80 B checked in the code) applies to one target and one build. Every node that verifies it stops pulling and offering, and stores it. It sends it up to 3 times checked in the code. It answers an offer of this build with the retract, at most every 30 s.

Schutz gegen Wiederholung

Ein mitgeschnittener alter Befehl gilt nach einem Neustart nicht wieder. Der Repeater hält den Zeitstempel eines Admins nur im RAM (Stock, also MeshCore unverändert). Darum speichert FUOTA den Zeitstempel des letzten ändernden Fern-Befehls (auto, apply). Gleiche und ältere Zeitstempel lehnt es ab. Stock-Befehle wie reboot schützt das nicht.

Am Testaufbau gemessen

Protection against replay

A recorded old command does not count again after a reboot. A repeater keeps an admin's timestamp only in RAM (stock, that is MeshCore unchanged). So FUOTA saves the timestamp of the last remote command that changes something (auto, apply). It refuses equal and older ones. Stock commands such as reboot are not covered.

Kennt der Repeater den Pfad zum Companion noch nicht, antwortet er per Flut. Eine Region ist der Flood-Scope, in dem eine Nachricht läuft. Ohne Default-Scope geht die Antwort ohne Region hinaus (Stock-Verhalten) gemessen. Mit Default-Scope geht sie in dessen Region im Code geprüft. Setze am Testaufbau darum vorher den Default-Scope.

Without a known path to the companion, the repeater answers with a flood. A region is the flood scope a message travels on. Without a default scope the answer goes out without a region (stock behaviour) measured. With a default scope it goes out in that region checked in the code. On the bench, set the default scope first.

Der Release-Build

Der Release-Build nutzt die Stock-Vorgaben für Frequenz, Bandbreite und Spreizfaktor. Er sendet beim Start ein Advert, die Ankündigung eines Knotens im Mesh. Gespeicherte Einstellungen und Schlüssel lässt er unverändert, denn FUOTA schreibt nur seine eigene Datei. Ein normaler Repeater ist er trotzdem nicht.

Unterschiede zum Stock-Build des FakeTec

Der Release-Build weicht vom Stock-Build des FakeTec (PlatformIO-Env ProMicro_repeater) in diesen Punkten ab:

  • Kein BLE in der App: start ota startet den BLE-DFU des Bootloaders.
  • Keine Anzeige: NullDisplayDriver statt des Anzeige-Treibers.
  • Board und Pins kommen zur Laufzeit aus dem Deskriptor.
  • Gebaut mit -Os statt -Ofast.
  • Zusätzlich die Sensor-Treiber für SHTC3, SHT4x, LPS22HB, INA260 und BME680.
  • Ein Update-Angebot flutet er höchstens einmal am Tag, in seiner Standard-Region (siehe Sicherheit).

Das stammt aus Build-Konfiguration und Code im Code geprüft. Was bei anderen Boards gegenüber Stock fehlt, steht unter Was noch offen ist. Die Größen stehen unter Flash.

Test-Build und Release-Build

Nur der Test-Build hat die Schalter des Testaufbaus:

  • SF7 und 1 dBm beim Start erzwungen
  • kein Advert
  • 10 % Budget
  • Testbefehle

Eine Build-Sperre bricht den Release-Build ab, sobald einer davon hineingerät.

Release und Test haben verschiedene Ziel-IDs. Jedes Anwenden prüft die Ziel-ID des Manifests. Eine Kampagne für den Testaufbau passt darum nie auf einen Release-Knoten.

Auch die Schlüssel sind getrennt. Ein Release-Build kompiliert nur mit einem eigenen Release-Schlüssel. Den Test-Schlüssel nimmt er nie im Code geprüft. Einen Release-Schlüssel gibt es noch nicht offen. Die Messung am Release-Build stammt von vor der Trennung, mit Test-Schlüssel. Mehr dazu: Was noch offen ist.

Am Release-Build gemessen (Stand 20. Oktober 2026)

  • 270.080 B, das sind 66 von 96 Seiten, mit signierten Angeboten gemessen
  • kein BLE-Symbol im Image gemessen
  • Die Build-Sperre greift bei allen 14 geprüften Schaltern gemessen. Dazu gehören die 7 Tage von delay, delay als Vorgabe und die Grenzen der Flut-Angebote.

The release build

The release build uses the stock defaults for frequency, bandwidth and spreading factor. It sends an advert at boot, a node's announcement to the mesh. It leaves saved settings and keys unchanged, because FUOTA writes only its own file. It is still not a normal repeater.

Differences from the stock build of the FakeTec

The release build differs from the stock build of the FakeTec (PlatformIO env ProMicro_repeater) in these points:

  • No BLE in the app: start ota starts the BLE DFU of the bootloader.
  • No display: NullDisplayDriver instead of the display driver.
  • Board and pins come from the descriptor at run time.
  • Built with -Os instead of -Ofast.
  • Plus the sensor drivers for SHTC3, SHT4x, LPS22HB, INA260 and BME680.
  • It floods an update offer at most once a day, in its default region (see Safety).

This comes from the build configuration and the code checked in the code. What other boards lack compared with stock is listed under What is still open. Sizes are under Flash.

Test build and release build

Only the test build has the bench switches:

  • SF7 and 1 dBm forced at boot
  • no advert
  • 10 % budget
  • test commands

A build guard stops the release build as soon as one of them gets in.

Release and test have different target IDs. Every apply checks the target ID of the manifest. So a campaign for the bench never fits a release node.

The keys are separate too. A release build compiles only with its own release key. It never uses the test key checked in the code. No release key exists yet open. The measurement of the release build predates the separation and used the test key. More: What is still open.

Measured on the release build (as of 20 October 2026)

  • 270,080 B, that is 66 of 96 pages, with signed offers measured
  • no BLE symbol in the image measured
  • The guard fires for all 14 switches tested measured. Among them: the 7 days of delay, delay as default, and the limits of flooded offers.
